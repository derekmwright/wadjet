## v0.24.0

A correctness and embedding release. **`read_csv`, `read_json`, `postgres_scan`
and `mysql_scan` stored every TIMESTAMP 1000 times too large; data you loaded
from them into a table before this release needs repairing, and the first
section says how.** An embedded program's tables now survive a restart. A file
reader in `FROM` over a local file publishes its schema before the query runs,
and a join of two readers keys on its condition. A value past the readers'
100-row inference sample that does not fit its column is an error instead of a
NULL. And a qualified reference names one relation in scope, as it does in
PostgreSQL. Ten issues close.

### File and database timestamps are stored in the engine's unit

`read_csv`, `read_json`, `postgres_scan` / `postgres_query` and `mysql_scan` /
`mysql_query` wrote a TIMESTAMP in microseconds into a column the engine reads
in milliseconds, so every value read 1000 times as far from 1970-01-01 as it
is: `2024-06-15 12:30:45` in a CSV file read as `56425-08-29 08:30:00`, and
`1969-07-20 20:17:40` as `1520-07-24 14:26:40`. They now store the same value
a `TIMESTAMP` literal of the same text does. This includes a `read_json`
timestamp nested in an array. An offset in the text is discarded, as
PostgreSQL's `timestamp` input discards it: `2001-02-03T04:05:06-07:00` reads
`2001-02-03 04:05:06`, where it read `33062-12-08 21:00:00`. (#1266)

**If you wrote reader output into a table** — `CREATE TABLE … AS SELECT` or
`INSERT … SELECT` from one of these functions — before this release, those
rows still hold the 1000-times value, and the upgrade does not change stored
data.

**The exact recovery is to read the source again with this release**, wherever
the file or database still exists: `CREATE TABLE … AS SELECT` into a new
table, or delete the affected rows and `INSERT … SELECT` them again. Either
way every row equals what the source reads today.

**Where the source is gone**, divide the stored value by 1000, once:

```sql
UPDATE events SET ts = FROM_UNIXTIME(EXTRACT(EPOCH FROM ts) / 1000);
```

It is exact, to the millisecond, for every row whose TRUE timestamp is before
`2255-06-05 23:47:34.740`: past that instant the stored value is larger than a
double holds exactly, and some rows come back one millisecond early (a row at
`9999-12-31 23:59:59.002` repairs to `.001`). A second run divides again.

Which rows to repair is a question of where each row came from, not of what
it holds. If the table was only ever loaded from `read_csv`, `read_json`,
`postgres_scan` / `mysql_scan` before the upgrade, repair the whole column.
If it mixes those rows with rows from other sources, select the reader rows
by what you know of their origin. A year test is a shortcut only when every
correctly loaded row is known to have a year of 9999 or less: in a table
loaded from these readers, any source instant after 1978-01-11 21:31:40.8
reads with a year above 9999, so

```sql
SELECT COUNT(*) FROM events WHERE EXTRACT(YEAR FROM ts) > 9999;
```

counts the rows that are wrong if the table was loaded from these readers. It
misses an earlier instant, which is wrong too but has an ordinary-looking
year (the 1969 value above reads 1520), and it catches a correct value with a
year above 9999 — which the embedded ingester can store — so in a mixed
table `WHERE EXTRACT(YEAR FROM ts) > 9999` on the `UPDATE` would rewrite that
correct value too. Where in doubt, re-read the source into a separate table
and compare.

Around the same fix:

- **`EXTRACT(EPOCH …)` and `TO_UNIXTIME` keep the milliseconds.** They
  answered whole seconds — `1718454645` for `2024-06-15 12:30:45.5` — and now
  answer `1718454645.5`. `FROM_UNIXTIME(1718454645.5)` keeps the `.5` where
  it answered `12:30:45`.
- **Year 1 is a timestamp.** `EXTRACT`, `DATE_TRUNC`, `TIME_BUCKET`,
  `YEAR()` / `HOUR()` and the other part functions, `TO_UNIXTIME` and
  `AT TIME ZONE` answered NULL for `0001-01-01 00:00:00`; they answer it.
- **`postgres_scan` stores every DATE.** A date before 1677-09-22 or after
  2262-04-11 was clamped to one of those two days.
- **A binary timestamp parameter is the instant it names.** Over the wire,
  a binary `timestamp` parameter dropped its fraction (`12:30:45.5` bound as
  `12:30:45`) and wrapped outside the years 1708–2292 (`1600-02-29` bound as
  `2184-09-18`). Both are bound exactly now. PostgreSQL's `infinity` and
  `-infinity` encodings are refused at Bind with `22023`, where they bound as
  `1999-12-31 23:59:59` and `2000-01-01 00:00:00`: TIMESTAMP here has no
  infinity, and the text `'infinity'` is refused as before.
- **A portal ends at Sync.** An `Execute` sent after `Sync` with no new
  `Bind` re-ran the previous statement; it is PostgreSQL's
  `34000 portal "" does not exist` now. A refused `Bind` no longer lets the
  `Describe` or `Execute` after it run the previous portal.

One rendering is unchanged: a TIMESTAMP inside an `ARRAY` prints as its
epoch-millisecond number (`[1718454645000]`), where PostgreSQL prints the
timestamp text. The stored value is right; the rendering is not (#1268).

### An embedded program's tables survive a restart

```go
db, err := wadjet.Open(ctx, wadjet.Config{DataDir: "./wadjet-data"})
```

keeps the Parquet data and the catalog in one local directory. A program that
creates a table, closes, and opens the directory again finds the table and
its rows; through v0.23.0 the only catalog an out-of-tree program could get
was an in-memory one, so the table was gone after the restart while its
Parquet file stayed on disk. (#1255)

- **It is the same directory the command line uses.**
  `wadjet query --storage-type=file --data-dir=./wadjet-data` and
  `wadjet serve --storage-type=file --data-dir=./wadjet-data` open the tables
  a program wrote there, and a program opens theirs.
- **`Config.CatalogDir`** is a persistent catalog on local disk beside any
  store — `wadjet.NewS3Store(…)` as `Config.Store`, for example.
- **One process holds a directory at a time.** A second `Open` of a held
  directory, in the same process or another, and a `wadjet serve` over it,
  are refused with `wadjet.ErrCatalogHeld`, naming the directory and the
  holder's process id. `DB.Close` releases it.
- A `Config` with no `DataDir` and no `CatalogDir` keeps the in-memory
  catalog, as before.

The getting-started program now runs twice against one directory, and
[Embedding](../embedding.md#persistence-a-catalog-that-survives-a-restart)
describes the layout and what a process kill leaves behind.

**`wadjet serve` needs a store.** Its `--storage-type` defaults to `s3`; with
no S3-compatible endpoint it stops at the bucket check. Without S3 it is

```
wadjet serve --storage-type=file --data-dir=./wadjet-data --pg-addr=:5432
```

which is what the README and the runbook now say. (#1256, in part)

### A file reader in FROM is a relation with a schema

`read_parquet`, `read_csv` and `read_json` over a regular local file now
publish their columns before the query runs: `read_parquet` from the file's
footer, `read_csv` and `read_json` from the same 100-row sample they have
always typed a file from. The table-function permission is decided before the
statement is bound, so a caller the policy refuses is refused with `42501`
and the file is never opened. (#1230)

- **An unknown column is `42703` at plan time.** `SELECT zz FROM
  read_json('x.json')` and `EXPLAIN` of it are refused before anything runs;
  `EXPLAIN` printed a plan.
- **A qualified star expands.** `SELECT f.* FROM read_json(…) AS f` answers
  the file's columns, where it was refused.
- **A reader's column carries its type.** `SUM` over a whole-number column is
  `numeric` on the wire, where it was `double precision`, as it is over a
  catalog `bigint` column.
- **A file with no rows is an empty relation.** A CSV holding only its header
  answers zero rows of its columns, where it failed with
  `XX000 the result has no columns at all`. A zero-byte JSON or CSV file,
  which declares no columns at all, is `0A000` naming the function and the
  file.

**A join of two readers keys on its condition.** `ON r2.c = r1.a` between a
four-row and a two-row file answered the CROSS PRODUCT, 8 rows, where
`ON r1.a = r2.c` and PostgreSQL answer 2; it answers 2 now, in either order,
for `read_json`, `read_csv` and their mixes, and a `LEFT JOIN` answers 4
where it answered 8. A bare reference to an unknown column in such a join
answered NULL for every row and is `42703`, including when one arm is a CTE.
These are the two shapes the v0.23.0 notes left open. (#1229, #1231)

**An unquoted dotted column name is a qualifier.** Over a file whose keys
contain dots — Zeek's `id.orig_h` — `SELECT id.orig_h FROM read_json(…)`
answered the column; it is now
`42P01 missing FROM-clause entry for table "id"`, as it has always been over
a catalog table with the same column and as it is in PostgreSQL. Quote the
name: `SELECT "id.orig_h" FROM read_json(…)` is unchanged.

An `http(s)` URL, `postgres_*` / `mysql_*` and an input that can only be read
once (a FIFO, `/dev/stdin`) are not read at plan time. They keep the
first-batch refusal and the `double precision` aggregates described on the
[differences page](../postgres-differences.md).

### A value past the inference sample is an error, not a NULL

`read_csv` and `read_json` type each column from the file's first 100 rows.
A later value that did not fit read as NULL or 0, or failed with an internal
error; it now refuses the statement with the SQLSTATE PostgreSQL's `COPY`
raises for the same field — `22P02`, `22003` for a number out of range,
`22007` for a timestamp — naming the input, the row, the column, the value
and both types:

```
read_json: /data/f.json: row 101 column "a": value 0.75 (double precision) is not of type bigint (the column's type was inferred from the file's first 100 rows)
```

A file of 100 integers and then `0.75` summed to `5050`; a string there
failed with `XX000 index out of range`. Over a glob, the error names the
matched file and its own row. A JSON `null` and an empty CSV field are still
NULL. A `LIMIT` that stops before the row still answers. (#1243, #1242 in
part)

- **`read_csv` reads a field the way `COPY` does.** A `bigint` column reads
  `0x1F` past the sample as 31, where it read NULL.
- **A glob of CSV files reads each later file's header as a header.** Two
  files of `a` + `1, 2` and `a` + `3` answer `COUNT(*) = 3` and `SUM(a) = 6`;
  they answered 4 and NULL. (#1247)
- **The sample types a number only in plain decimal spelling**, so a spelling
  is read alike inside the sample and after it. Some columns change type:
  a `read_csv` column sampled as `' 5'` is `bigint` (it was text); one sampled
  as `1_000`, `0x1p-2` or `1e-400` is `text` (it was `double precision`
  `1000`, `0.25` and `0`); `0x1F`-style values stay `text`; and a `read_json`
  number no `double precision` holds, such as `1e999`, is `text` (it was `0`).
- A `read_json` object with an empty key (`{"": 1}`) reads; it failed with an
  internal error.

A key that first appears after the sample is still not a column (#1242).

### A qualified reference names one relation in scope

A `JOIN`'s `ON` clause may name only the relations already joined in its own
`FROM` item. A relation joined LATER, and one in a different comma-separated
`FROM` item, are refused with PostgreSQL's `42P01`:

```sql
-- missing FROM-clause entry for table "j"
SELECT a.id FROM lat_ord a JOIN lat_item b ON j.id = a.id JOIN lat_item j ON j.id = b.id
-- invalid reference to FROM-clause entry for table "a"
SELECT a.id FROM lat_ord a, lat_item b JOIN lat_item c ON a.id = c.order_id
```

Both answered rows. (#1220)

A window function's `PARTITION BY`, `ORDER BY` and argument are resolved the
same way. `COUNT(*) OVER (PARTITION BY zz.id)` with no relation `zz` answered
one partition per row on a bare `id`; it is `42P01`. A table name the `FROM`
reads under an alias (`PARTITION BY lat_ord.id … FROM lat_ord o`) is refused
with PostgreSQL's hint to use the alias, where it answered, and so is a
qualifier naming a relation both arms of a self-join scan, which bound one of
them. A bare `PARTITION BY id` that two joined relations publish is `42702`,
where it bound one. (#1161, #1162)

The same rule reaches a qualified star (`SELECT zz.*`), a reference under a
`SELECT *` (`ORDER BY zz.id` answered), and `FROM t, t`, which is
`42712 table name "t" specified more than once` where it answered the cross
product. Every one of these is decided at plan time, so it is the same on
every execution path.

### Reference

- 387 built-in scalar functions and 29 aggregates.
- Every deliberate divergence from PostgreSQL is listed on the
  [differences page](../postgres-differences.md) and in ADR-0012. Two left
  it in this release (an `ON` clause naming a comma sibling, and a bare
  `PARTITION BY` name two relations publish, now refused as PostgreSQL
  refuses them), the two wrong-value entries for a join of two readers are
  gone with the fix, and two joined it: TIMESTAMP has no infinity, and a
  reader whose input declares no columns is `0A000` where PostgreSQL has a
  zero-column relation.
- ADR-0041 records that an embedded catalog is a directory opened the way
  `serve` opens it. ADR-0039 §3 records that the table-function capability is
  authorized before the statement binds, which is what lets a reader publish
  its schema, and what a value past the sample does; §9 records the join
  key's side. ADR-0034 records the doors' order.
