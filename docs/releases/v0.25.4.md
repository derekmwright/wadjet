## v0.25.4

A patch release for correctness and PostgreSQL compatibility. It covers scalar subqueries, numeric values, text rendering, parameter types, reader inference, joins, window defaults, temporal values and repeated CTE reads. **The first section lists what a client or a stored query sees differently after the upgrade.**

### Behaviour changes

**New refusals.**

- `SELECT 3 || 3` and `SELECT DATE '2024-03-04' * 3` now raise `42883`; v0.25.3 answered `33` and `59358`.
- `SELECT format('%d', 3)` now refuses the format specifier; v0.25.3 answered `%!d(string=3)`.
- `SELECT format('%5.2s', 'abc')` now raises `22023`; v0.25.3 answered `   ab`.
- `SELECT json_build_object(ARRAY[1], 3)` now raises `22023`; v0.25.3 answered `{"[1]" : 3}`.
- With INTEGER `n = 7` and a DATE parameter bound NULL, `SELECT n FROM t WHERE n = $1 OR $1 IS NULL` now raises `42883`; v0.25.3 returned 7.
- `SELECT DATE '2024-03-04 12:00:00Z+05'` now raises `22007`, where v0.25.3 answered `2024-03-04`.
- `SELECT CAST((-9223372036854775809) AS BIGINT)` now raises `22003`; v0.25.3 answered `-9223372036854775808`.
- For a JSON file with 100 rows containing only `id` followed by `{"id":101,"k":7}`, `SELECT * FROM read_json(f) WHERE id = 101` now refuses the late key `k`; v0.25.3 returned only `id = 101`.
- A nested field first appearing at row 101 is refused too: `SELECT * FROM read_json(f) WHERE id = 101` over `m = {"x":101,"y":2}` now refuses field `y`, where v0.25.3 returned only `m = {"x":101}`.
- Over three rows, `SELECT count(*) FROM t TABLESAMPLE BERNOULLI (0)` now answers 0 and the same statement with `(101)` refuses an out-of-range percentage; v0.25.3 answered 3 for both.
- `SELECT CAST('1_0' AS REAL)` and `SELECT CAST('1e-46' AS REAL)` now refuse the input text and the out-of-range value respectively; v0.25.3 answered 10 and 0.
- `CREATE TABLE t (a BIGINT); INSERT INTO t SELECT CAST('9223372036854775808' AS DOUBLE PRECISION)` now refuses the out-of-range value and leaves the table empty; v0.25.3 stored `-9223372036854775808`.
- Over bigint values 10 and 20, `SELECT LAG(b, 0, 'a') OVER (ORDER BY id) FROM t` now raises `22P02`; v0.25.3 answered `10, 20`.
- Over a VARCHAR column holding `8`, `SELECT mod(s, 2) FROM t` now refuses `text % integer`; v0.25.3 answered 0.
- `SELECT mod(DATE '2024-03-04', 2)` now raises `42883`; v0.25.3 answered 0.
- Over `n = NUMERIC(10,2) 2.25`, `SELECT SUM(n % '0') FROM t` now raises `22012`; v0.25.3 answered 0.
- Comparisons `ts < 'now'` and `ts < 'today'` now raise `22007` over a TIMESTAMP row at `1970-01-01 00:00:00`, where v0.25.3 returned no rows ([temporal r25](../adr/0012-divergences/temporal.md)).
- Over a TIMESTAMP row at `1970-01-01 00:00:00`, `SELECT ts FROM t WHERE ts = 'garbage'` now raises `22007`; v0.25.3 returned the row.
- Over a TIMESTAMP row at `1970-01-01 00:00:00`, `SELECT ts FROM t WHERE ts < 'tomorrow'` now raises `22007`; v0.25.3 returned no rows.
- `INSERT INTO t VALUES ('\q')` into BYTES now refuses the invalid escape and leaves the table empty; v0.25.3 stored `5c71`.
- `SELECT encode('\q', 'hex')` now raises `22P02`; v0.25.3 answered `5c71`.

**Declared types and stored values.**

- Over `c.f = DOUBLE 6.5` and `x.v = INTEGER 1`, the correlated `(SELECT c.f + x.v FROM x WHERE x.id = c.id)` now declares double precision and answers 7.5; v0.25.3 declared integer and answered 7.
- Inserting that subquery into an INTEGER column now stores 8, where v0.25.3 stored 7.
- `SELECT ascii('abc')` now declares integer (OID 23), where v0.25.3 declared double precision (OID 701).
- For `a = ARRAY[4]` and `n = NUMERIC(10,2) 10.00`, `SELECT a[1] * n FROM t` now declares numeric (OID 1700) instead of double precision (OID 701).
- `SELECT $1` with a declared bigint parameter now declares bigint (OID 20), where v0.25.3 declared text (OID 25).
- `SELECT $1` with a timestamptz parameter bound to `2024-03-04 17:00:00+05` now declares timestamp (OID 1114) and prints `2024-03-04 12:00:00`; v0.25.3 declared text and printed the original text.
- `CREATE TABLE t (v FLOAT); INSERT INTO t VALUES (674999997); SELECT v FROM t` now declares double precision (OID 701) and reads `674999997`; v0.25.3 declared real (OID 700) and read `675000000`.
- A FLOAT column created at v0.25.3 keeps its real declaration and stored value: `SELECT v FROM t` still reads `675000000` in the example above.
- The described parameter of `SELECT $1::FLOAT` changes from unspecified (0) to float8 (701).
- `CREATE TABLE z (v DOUBLE PRECISION)` now succeeds instead of raising `42601`, and the REAL, FLOAT4 and FLOAT8 column spellings now succeed instead of raising `42704`.
- For a CSV column containing integers 1–100 followed by 0.75, `SELECT SUM(a) FROM read_csv(f, sample_size = -1)` now answers 5050.75; v0.25.3 refused the negative named argument.
- `SELECT 9223372036854775808` now declares numeric and prints `9223372036854775808`; v0.25.3 declared double precision and printed `9.223372036854776e+18`.
- Over bigint rows 30 and NULL, `SELECT COALESCE(b, 14.0000000000000000001) FROM t ORDER BY b` now declares numeric and prints `30.0000000000000000000, 14.0000000000000000001`; v0.25.3 declared double precision and printed `30, 14`.
- Over INTEGER `i = 3`, `SELECT MOD(i, '2.5') FROM t` now declares double precision and answers 0.5; v0.25.3 declared integer and answered 0 ([numeric-decimal r21](../adr/0012-divergences/numeric-decimal.md)).
- Over bigint values 10 and 20 ordered by `id`, `SELECT LAG(b, 1, 2.5) OVER (ORDER BY id) FROM t` now declares numeric (OID 1700) and prints `2.5, 10.0`; v0.25.3 declared bigint (OID 20) and printed `2, 10`.
- Over bigint values 10 and 20 ordered by `id`, `SELECT LEAD(b, 1, 2.5) OVER (ORDER BY id) FROM t` now declares numeric and prints `20.0, 2.5`; v0.25.3 declared bigint and printed `20, 2`.
- Over bigint values 10 and 20 ordered by `id`, `INSERT INTO dst SELECT LAG(b,1,2.5) OVER (ORDER BY id), LAG(b,1,2.5) OVER (ORDER BY id), LAG(b,1,2.5) OVER (ORDER BY id) FROM t` into INTEGER, NUMERIC(10,2) and DOUBLE columns now stores `3, 2.50, 2.5` for the default row; v0.25.3 stored `2, 2.00, 2`.
- `CREATE TABLE c AS SELECT id, LAG(b, 1, CAST(NULL AS NUMERIC)) OVER (ORDER BY id) AS v FROM t` over bigint `b` now succeeds with a scale-zero numeric column, so `INSERT INTO c VALUES (9, 0.75)` stores 1; v0.25.3 refused the table creation ([aggregates-windows r24](../adr/0012-divergences/aggregates-windows.md)).
- Over INTEGER `i`, `SELECT i % 3 FROM t` now declares integer (OID 23) instead of bigint (OID 20).
- `SELECT CAST('infinity' AS TIMESTAMP)` now prints `infinity`, where v0.25.3 refused the input.
- `INSERT INTO t VALUES (TIMESTAMP 'infinity', DATE '-infinity')` now stores and reads `infinity, -infinity` in TIMESTAMP and DATE columns, where v0.25.3 refused the insert.
- `CREATE TABLE t (b BYTES); INSERT INTO t VALUES ('\x6869'); SELECT encode(b, 'hex') FROM t` now reads `6869`, where v0.25.3 read `5c7836383639`.
- The previously stored BYTES row keeps its bytes: `SELECT encode(b, 'hex') FROM t` still returns `5c7836383639` after upgrading.
- `INSERT INTO dst SELECT b FROM src` from BYTES `hi` into VARCHAR now stores `\x6869`; v0.25.3 raised `42804`.
- A recursive CTE seeded by `(SELECT n FROM t)` over `NUMERIC(10,2) 2.25`, adding 1 twice, now answers `2.25, 3.25, 4.25` instead of v0.25.3’s `42804`; the remaining modifier difference is [recursion r11](../adr/0012-divergences/recursion.md).
- With an INTEGER target `t(id, n)`, `INSERT INTO t VALUES (2, $1)` binding 2.5 now stores 2 through parameter inference; v0.25.3 raised `22P02` (wire measurements from the supplied notes).
- `SELECT CAST('2024-03-04 12:00:00+000130' AS TIMESTAMP)` now answers `2024-03-04 12:00:00`; v0.25.3 raised `22007`.
- The column declaration in `CREATE TABLE t (v FLOAT8)`, also accepted as `FLOAT8` in HTTP/gRPC CreateTable and as a container element declaration, now succeeds where v0.25.3 refused the type with `42704` (wire measurements from the supplied notes).
- For a JSON file with 100 rows containing only `id` followed by `{"id":101,"k":7}`, `SELECT * FROM read_json(f, sample_size = 101) WHERE id = 101` now returns `id = 101, k = 7`; v0.25.3 returned only `id = 101`.
- With `sample_size = -1`, that query now returns `id = 101, k = 7`; v0.25.3 refused the negative named argument.
- Over INTEGER values 1 and 2, `SELECT CAST(g AS FLOAT) FROM t GROUP BY CAST(g AS FLOAT8) ORDER BY 1` now answers `1, 2`; v0.25.3 raised `42803`.
- `SELECT ABS(-1), MOD(8, 2), MOD(8, 2.5)` now declares bigint, integer and numeric (OIDs 20, 23 and 1700); v0.25.3 declared all three double precision (OID 701).
- Over three rows, `SELECT count(*) FROM t TABLESAMPLE BERNOULLI (25*4)` now answers 3; v0.25.3 raised `42601`.
- Over a BYTES row containing a backslash, `SELECT count(*) FROM t WHERE b = $1` with that binary bytea parameter now answers 1; v0.25.3 raised `22P02` (wire measurements from the supplied notes).

**Printed text and error codes.**

- For `a = ARRAY[4]` and `n = NUMERIC(10,2) 10.00`, `SELECT a[1] * n FROM t` now writes the CLI JSON string `"40.00"`; v0.25.3 wrote the JSON number `40`.
- Over that numeric column, `SELECT ARRAY[n, 1], json_build_object('v', n) FROM t` now prints `{10.00,1.00}` and `{"v" : 10.00}`; v0.25.3 printed `{10.00,0.01}` and `{"v" : "10.00"}`.
- `SELECT json_build_object('d', DATE '2024-03-04', 'ts', TIMESTAMP '2024-03-04 12:00:00')` now prints ISO strings for both values; v0.25.3 printed `19786` and `1709553600000`.
- `SELECT json_build_object('o', json_build_object('a', 1))` now prints `{"o" : {"a" : 1}}`, where v0.25.3 nested the inner object as a string.
- `SELECT format('%s|', NULL), regexp_replace('-10.50', '0', 'z')` now answers `|, -1z.50`; v0.25.3 answered `%!s(<nil>)|, -1z.5z`.
- Over a double column containing Infinity, NaN and -0, `SELECT c, count(*) FROM t GROUP BY c ORDER BY c` now prints the zero group as `-0, 1`, where v0.25.3 printed `0, 1`.
- `SELECT CAST('-2.5' AS DOUBLE PRECISION) % 2.5` now prints `0`, where v0.25.3 printed `-0`.
- For a TIMESTAMP column containing `1969-12-31 23:59:59.999`, `SELECT CAST((SELECT ts FROM t) AS VARCHAR)` now prints that timestamp; v0.25.3 printed `-1`.
- `SELECT CAST(1 AS FLOAT(1))` now labels its OID 700 column `float4`; v0.25.3 labelled it `float8`.
- Over `n = NUMERIC(10,2) 2.25`, `SELECT CAST(n AS DATE) FROM t` now raises `42846`; v0.25.3 raised `22007`.
- For a CSV column containing integers 1–100 followed by 0.75, `SELECT SUM(a) FROM read_csv(f)` still raises `22P02`, but now appends `sample_size = -1 infers it from every row`; v0.25.3 ended the message after describing the first 100 rows.
- Over bigint values 10 and 20 ordered by `id`, `SELECT LAG(b, 1, DATE '2024-03-04') OVER (ORDER BY id) FROM t` now raises `42883`; v0.25.3 raised `42000`.
- `SELECT regexp_replace('abc', 'a', 'x', 'n')` now raises `0A000` for the flag, where v0.25.3 raised `42883` for the four-argument call.

**Work and memory.** Float MAX no longer uses the file-statistics shortcut, so it requires a column read. Whole-input reader inference (`sample_size = -1`) makes a second pass over the input. A volatile CTE with multiple readers has one shared result on the embedded engine, filled on demand and spilled past its memory budget. Deep declaration walks and MOD chains use memoized walks.

- In a 200-iteration local wire run over 50 one-row files with an INSERT before every Parse, `SELECT count(*) FROM n1 WHERE n = $1 AND f < $2 + 1` had a median Parse-and-Describe time of 3.58 ms now, compared with 2.11 ms at v0.25.3.
- Over three rows, `SELECT count(*) FROM t TABLESAMPLE BERNOULLI (NULL) WHERE false` now answers 0 without starting the sampled scan; v0.25.3 raised `42601`.
- After deleting the even IDs from INTEGER IDs 1–8, `SELECT id FROM t TABLESAMPLE BERNOULLI (100) ORDER BY id` now samples only the remaining rows and answers `1, 3, 5, 7`; v0.25.3 returned all eight IDs.
- Over 4,096 rows, `SELECT count(DISTINCT CAST(now() AS TEXT)) FROM t` answered 4 in the v0.25.3 embedded run and now answers 1.

### Scalar subqueries keep their types

For a TIMESTAMP column containing `1969-12-31 23:59:59.999`, `SELECT CAST((SELECT ts FROM t) AS VARCHAR)` now prints that timestamp; v0.25.3 printed `-1`. Over `c.f = DOUBLE 6.5` and `x.v = INTEGER 1`, the correlated `(SELECT c.f + x.v FROM x WHERE x.id = c.id)` now declares double precision and answers 7.5; v0.25.3 declared integer and answered 7. Inserting that subquery into an INTEGER column now stores 8, where v0.25.3 stored 7. For `a = ARRAY[4]` and `n = NUMERIC(10,2) 10.00`, `SELECT a[1] * n FROM t` now writes the CLI JSON string `"40.00"`; v0.25.3 wrote the JSON number `40`. A recursive CTE seeded by `(SELECT n FROM t)` over `NUMERIC(10,2) 2.25`, adding 1 twice, now answers `2.25, 3.25, 4.25` instead of v0.25.3’s `42804`; the remaining modifier difference is [recursion r11](../adr/0012-divergences/recursion.md). For `d = DATE '9999-12-31'` and `ts = TIMESTAMP '2024-03-04 12:00:00'`, `SELECT d FROM t WHERE d = (SELECT d FROM t)` now finds the row and `SELECT (SELECT max(ts) FROM t) + INTERVAL '1 hour' AS v` answers `2024-03-04 13:00:00`; v0.25.3 found no row and left the timestamp at 12:00. (#1422, #1427, #1428, #1431)

### JSON, formatting and regular expressions

`SELECT json_build_object('d', DATE '2024-03-04', 'ts', TIMESTAMP '2024-03-04 12:00:00')` now prints ISO strings for both values; v0.25.3 printed `19786` and `1709553600000`. `SELECT json_build_object('o', json_build_object('a', 1))` now prints `{"o" : {"a" : 1}}`, where v0.25.3 nested the inner object as a string. `SELECT format('%s|', NULL), regexp_replace('-10.50', '0', 'z')` now answers `|, -1z.50`; v0.25.3 answered `%!s(<nil>)|, -1z.5z`. A derived JSON value still nests as a string in both versions: `SELECT json_build_object('o', x) FROM (SELECT json_build_object('a', 1) AS x) s` prints `{"o" : "{\"a\" : 1}"}` ([other r16](../adr/0012-divergences/other.md)). (#1466, #1467, #1474, #1481)

### Concurrent casts

`SELECT CAST('1.25' AS NUMERIC(10,2)), CAST('abcd' AS VARCHAR(2))` answers `1.25, ab` in both versions. The parsed decimal and string-length destinations now use one atomic pointer each, correcting a data race when one compiled cast is evaluated concurrently. This is a concurrency correction with no separate divergence catalog row.

### Parameter types over pgwire

With a DATE row `2024-03-04` and a TIMESTAMP parameter `2024-03-04 12:00:00`, `SELECT d FROM t WHERE d = $1` now returns no row; v0.25.3 returned the DATE. `SELECT $1` with a declared bigint parameter now declares bigint (OID 20), where v0.25.3 declared text (OID 25). A declared text parameter bound to `7` still matches an INTEGER 7 in `SELECT n FROM t WHERE n = $1` in both versions ([parameters-pgwire r5](../adr/0012-divergences/parameters-pgwire.md)). (#1410, #1426)

### FLOAT columns use double precision

`CREATE TABLE t (v FLOAT); INSERT INTO t VALUES (674999997); SELECT v FROM t` now declares double precision (OID 701) and reads `674999997`; v0.25.3 declared real (OID 700) and read `675000000`. A FLOAT column created at v0.25.3 keeps its real declaration and stored value: `SELECT v FROM t` still reads `675000000` in the example above. `SELECT CAST('674999997' AS REAL)` still prints `675000000` over pgwire in both versions, while PostgreSQL prints `6.75e+08`. The real text-format difference has no catalog row. (#1405, #1464)

### A spilled outer join keeps the preserved values

With an empty `sj_e`, 2,048 preserved rows and a 256 KiB budget, `SELECT p.id, p.k_int, p.v_dec, p.v_arr, e.k_int, e.ey FROM sj_e e RIGHT JOIN sj_p_b2048 p ON e.k_int = p.k_int` now returns all 2,048 rows with the empty side NULL; v0.25.3 failed with `cannot store int64 into ARRAY vector`. The partition replay now uses the declared probe schema and the join’s output column mapping. The remaining distributed same-name column problem has no catalog row. (#1359)

### Exact numeric values and integer casts

`SELECT CASE WHEN true THEN 14.0000000000000000001 END = 14, CAST(5 / 2.0 AS INTEGER)` now answers false and 3; v0.25.3 answered true and 2. `SELECT CAST(9000000000 AS BIGINT) * 10000000 * CAST(10.00 AS NUMERIC(10,2)) - 3` now answers the exact `899999999999999997.00`; v0.25.3 answered `900000000000000000`. Over `t.id = 1`, `SELECT CAST(s.x AS INTEGER) FROM (SELECT DISTINCT 5 / 2.0 + t.id * 0 AS x FROM t) s` still answers 2 in both versions ([dml-assignment r2](../adr/0012-divergences/dml-assignment.md)). For `i = INTEGER 3` and `n = NUMERIC(10,2) 2.25`, `SELECT CAST(i AS INTEGER) / n FROM t` still answers double precision `1.3333333333333333` in both versions ([numeric-decimal r19](../adr/0012-divergences/numeric-decimal.md)). (#1386, #1392; #1450 remains open.)

### Reader inference past the sample

For a JSON file with 100 rows containing only `id` followed by `{"id":101,"k":7}`, `SELECT * FROM read_json(f) WHERE id = 101` now refuses the late key `k`; v0.25.3 returned only `id = 101`. With `sample_size = -1`, that query now returns `id = 101, k = 7`; v0.25.3 refused the negative named argument. For a CSV column containing integers 1–100 followed by 0.75, `SELECT SUM(a) FROM read_csv(f, sample_size = -1)` now answers 5050.75; v0.25.3 refused the negative named argument. Whole-input inference requires a second pass over the input. Remaining reader grammar differences are listed in [table-functions r3–r6](../adr/0012-divergences/table-functions.md); [ADR-0039 §3](../adr/0039-a-table-function-in-from-is-a-relation.md) describes inference. (#1242)

### TABLESAMPLE checks its percentage

Over three rows, `SELECT count(*) FROM t TABLESAMPLE BERNOULLI (0)` now answers 0 and the same statement with `(101)` refuses an out-of-range percentage; v0.25.3 answered 3 for both. `SELECT CAST('1_0' AS REAL)` and `SELECT CAST('1e-46' AS REAL)` now refuse the input text and the out-of-range value respectively; v0.25.3 answered 10 and 0. `SELECT count(*) FROM t TABLESAMPLE BERNOULLI (100) REPEATABLE (1)` still raises `42601` in both versions ([other r17](../adr/0012-divergences/other.md)). ### Float assignment checks the integer range

`CREATE TABLE t (a BIGINT); INSERT INTO t SELECT CAST('9223372036854775808' AS DOUBLE PRECISION)` now refuses the out-of-range value and leaves the table empty; v0.25.3 stored `-9223372036854775808`. For a double array holding 2.5 and 1.5, `SELECT CAST(a AS BIGINT[]) FROM t` still answers `{3,2}` in both versions, where PostgreSQL answers `{2,2}`; this remaining array-conversion difference has no catalog row. The conversion now uses a half-open upper bound at 2^63. (#1484)

### LAG and LEAD widen for the default

Over bigint values 10 and 20 ordered by `id`, `SELECT LAG(b, 1, 2.5) OVER (ORDER BY id) FROM t` now declares numeric (OID 1700) and prints `2.5, 10.0`; v0.25.3 declared bigint (OID 20) and printed `2, 10`. Over bigint values 10 and 20, `SELECT LAG(b, 1, '7') OVER (ORDER BY id) FROM t` now answers `7, 10`; v0.25.3 failed with `cannot store string into INT64 vector`. Over bigint `b` and double `d`, `SELECT LAG(b, 1, (SELECT max(d) FROM t)) OVER (ORDER BY id) FROM t` still fails with `cannot store string into INT64 vector` in both versions ([aggregates-windows r23](../adr/0012-divergences/aggregates-windows.md)). The column-scale limitation is recorded in [numeric-decimal r18](../adr/0012-divergences/numeric-decimal.md) and [aggregates-windows r24](../adr/0012-divergences/aggregates-windows.md). (#1435, #1436)

### The percent operator uses MOD

Over `i = INTEGER 3, n = NUMERIC(10,2) 2.25`, `SELECT SUM(n % '2.5'), SUM(i % NULL) FROM t` now answers `2.25, NULL`, where v0.25.3 answered `0, 0`. Over INTEGER `i`, `SELECT i % 3 FROM t` now declares integer (OID 23) instead of bigint (OID 20). `SELECT 2 ^ 3 % 5` still answers 3 in both versions, where PostgreSQL refuses the double operand ([numeric-decimal r11](../adr/0012-divergences/numeric-decimal.md)). (#1527)

### Temporal comparisons refuse unreadable text

For a TIMESTAMP row at `1970-01-01 00:00:00`, `SELECT ts FROM t WHERE ts = 'garbage'` now raises `22007`; v0.25.3 returned the row. Comparisons `ts < 'now'` and `ts < 'today'` now raise `22007` over a TIMESTAMP row at `1970-01-01 00:00:00`, where v0.25.3 returned no rows ([temporal r25](../adr/0012-divergences/temporal.md)). Use CURRENT_TIMESTAMP and CURRENT_DATE for the clock words. (#1512)

### Float maxima and signed zero

Over a double column containing Infinity, NaN and -0, `SELECT min(c), max(c) FROM t` now answers `-0, NaN`, where v0.25.3 answered `-0, Infinity`. Over a double column containing Infinity, NaN and -0, `SELECT c, count(*) FROM t GROUP BY c ORDER BY c` now prints the zero group as `-0, 1`, where v0.25.3 printed `0, 1`. On the distributed path, a comparison against a scalar subquery that answers NaN or an infinity still compares against NULL (#1576, no catalog row). Float MAX no longer uses the file-statistics shortcut, so it requires a column read. (#1488, #1489)

### Infinite TIMESTAMP and DATE values

`SELECT CAST('infinity' AS TIMESTAMP)` now prints `infinity`, where v0.25.3 refused the input. `INSERT INTO t VALUES (TIMESTAMP 'infinity', DATE '-infinity')` now stores and reads `infinity, -infinity` in TIMESTAMP and DATE columns, where v0.25.3 refused the insert. For the finite TIMESTAMP `1970-01-01 00:00:00`, `SELECT ts FROM t WHERE ts < 'infinity'` now returns the row; v0.25.3 returned none. `SELECT TIMESTAMP 'infinity' < ALL ('{infinity}')` still raises `22007` in both versions; the quoted-array input limitation is tracked by #1568. The remaining temporal-operation limits are in [temporal r2](../adr/0012-divergences/temporal.md). (#1567)

### One clock per statement

Over 4,096 rows, `SELECT count(DISTINCT CAST(now() AS TEXT)) FROM t` answered 2 in the v0.25.3 run and now answers 1. `SELECT 1 LIMIT CAST(extract(epoch FROM now()) AS BIGINT) % 7 + 1` still raises `42601` in both versions ([temporal r27](../adr/0012-divergences/temporal.md)). The clock is captured at statement start and carried through expression compilation and constant folding. The remaining transaction-granularity difference is [temporal r26](../adr/0012-divergences/temporal.md). (#1566)

### Text input to BYTES

`CREATE TABLE t (b BYTES); INSERT INTO t VALUES ('\x6869'); SELECT encode(b, 'hex') FROM t` now reads `6869`, where v0.25.3 read `5c7836383639`. The previously stored BYTES row keeps its bytes: `SELECT encode(b, 'hex') FROM t` still returns `5c7836383639` after upgrading. Over a BYTES value `hi` and VARCHAR `hi`, `SELECT b || s FROM t` still prints `hihi` in both versions ([text-collation r13](../adr/0012-divergences/text-collation.md)). (#1501)

### A volatile CTE read twice

On the embedded engine, `WITH s AS (SELECT sum(random()) AS r FROM cm_big) SELECT count(*) FROM cm_p WHERE (SELECT r FROM s) <> (SELECT r FROM s)` over 4,096 source rows and three outer rows now answers 0; v0.25.3 answered 3. On the stage DAG, the issue’s statement still answers 3 because each consumer evaluates the volatile body ([other r24](../adr/0012-divergences/other.md)). A CTE read once from a correlated subquery still runs per outer row: `WITH s AS (SELECT random() r) SELECT count(DISTINCT (SELECT r + t.id*0 FROM s)) FROM t` over 50 rows answers 50 in both versions ([other r27](../adr/0012-divergences/other.md)). The embedded shared result is filled one batch at a time on demand, with spill files when needed. (#1531)
