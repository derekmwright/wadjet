## v0.23.0

A table-function and command-line release. A table function in `FROM` is a
relation now: it publishes a column list, a reference to a column it does not
publish is refused instead of answering NULL for every row, and its columns
carry their declared type. `generate_series` answers PostgreSQL's series. The
`wadjet` CLI prints the columns the wire carries, in every output format — the
caveat the v0.22.0 notes carried is gone. And a planner setting belongs to the
database that holds it rather than to the process it runs in. Seven issues
close.

### A table function in FROM is a relation

Every rule that holds for a base table's columns holds for a table function's.

- **A reference to a column it does not publish is `42703`, naming the
  column.** It used to answer NULL for every row, on the wire and through the
  embedded API alike. Where the refusal is made depends on where the column
  list comes from: `generate_series` and `unnest` declare theirs from the
  call, so an unknown column is refused at plan time exactly as over a base
  table, while a file or database reader's list is its input's, and the
  refusal is made when it produces its first batch and names what the relation
  publishes — `column "zz" does not exist: the table function "read_json"
  publishes a, b`. The planner does not open your file or run your remote
  query to bind your statement: the column binding happens before the
  table-function capability is authorized, so reading the input there would
  open it for an identity that may not be allowed to. (#1210)
- **A table function's column carries its type.** `generate_series(1, 3)`
  publishes `integer` and `generate_series(3000000000, 3000000001)` publishes
  `bigint`, which is the overload PostgreSQL resolves for the same call, and
  the declaration is what the consumers read: `SUM(x)` is `bigint`, `AVG(x)`
  is `numeric`, `MIN`/`MAX` keep `integer`, and `unnest` follows the same
  rule. The column used to be `bigint` whatever the call, and every aggregate
  over it `double precision` — so `SUM(x) FROM generate_series(9007199254740993,
  9007199254740993)` answered `9.007199254740992e+15` for a value the same
  column through a catalog table has always returned exactly. (#1211)
- **`generate_series` never flips your step.** `generate_series(5, 1)` is an
  empty relation, as it is on PostgreSQL; it used to answer the descending
  series `5 4 3 2 1`. The descending series is `generate_series(5, 1, -1)`,
  which now parses — a negative step directly in front of a number used to be
  a syntax error, so the series that was answered could not be asked for. A
  zero step is `22023 step size cannot equal zero`. And a series whose bound
  sits at the 64-bit edge ends there: `generate_series(9223372036854775805,
  9223372036854775807)` is three rows, where the counter used to wrap past the
  bound, the loop's exit was never reached and the query did not end. (#1202)
- **A correlated subquery over a table function binds the outer row**, whether
  the function is the `FROM` item or an arm of a join inside the subquery.

  ```sql
  SELECT n, (SELECT COUNT(*) FROM generate_series(1, 2) AS g(x) WHERE x <= n)
  FROM tfouter ORDER BY n
  ```

  answers `1, 2, 2` — it answered `0` for every outer row, and NULL where the
  aggregate was a `MAX`. The per-row re-run rebuilds the statement's text, and
  it wrote a `FROM` item as its bare NAME; for a table function the name alone
  is not the relation, so the rebuilt statement read a base table nothing
  declares. (#1203)
- **`ORDER BY -a` over a reader sorts by the negation.** It sorted ascending
  by `a`, because an undecided operand made the negation a string.

Five boundaries follow from where a reader's column list comes from, and each
is on the [differences page](../postgres-differences.md) with its reason: a
reader that produces NO batch is never measured, so an unknown column over an
empty file answers zero rows where PostgreSQL raises, and `EXPLAIN` over such
a statement does not refuse; an aggregate over a reader's column still
declares `double precision` and `SELECT f.* FROM read_json(…) AS f` is still
`0A000`, because both need a column list at plan time; a `FROM` alias does not
rename a single-column function's column, which PostgreSQL does; and
`generate_series(…) WITH ORDINALITY` publishes one column where PostgreSQL
publishes two.

One shape is still wrong rather than merely different, and it is worth
knowing: **a BARE reference to an unknown column in a join holding TWO file
readers answers NULL for every row** where PostgreSQL raises `42703`. Neither
arm can be held to a bare name when both have unknown column lists, so the
check is declined. Qualify the reference — `SELECT b.zz FROM read_json('a.json')
b JOIN read_json('a.json') c ON b.a = c.a` IS refused — or read one of the two
through a CTE. (#1229, open)

### The `wadjet` CLI prints the columns the wire carries

A result may hold two output columns of one name: `SELECT abs(a), abs(b)`, or
a star over a `JOIN … USING` whose arms share a tail name. The PostgreSQL wire
carries both positionally and always has; the command-line output was keyed by
column name, so it could not.

- **The table and CSV forms print each column's own value under its own
  heading**, repeating the heading. `SELECT * FROM la JOIN rb USING (id)` over
  a one-row fixture prints `2, 20, 200, 300, 99` — the values `psql` shows
  against the same server. It printed `2, 99, 200, 300, 99`, one column's
  value under another's heading.
- **The JSON form emits both keys, in column order**, the way PostgreSQL's
  `row_to_json` does: `{"u": 1, "u": 2}` for `SELECT 1 AS u, 2 AS u`. It
  emitted `{"u": 2}` — a single key, with the other column dropped from the
  output entirely. JSON is the default format.
- **JSON keys now follow COLUMN order for every result**, duplicate names or
  not, where `encoding/json` sorted them alphabetically. That is the only
  change to the output of a result whose column names are unique.
- `query`, the interactive `shell` and the catalog-free `query` path all
  render this way; the `mcp` door was already positional.

(#1218 — the caveat in the v0.22.0 notes describes the old behaviour.)

### Every command's database carries the flags you typed

`--memory-budget`, `--spill-dir`, `--sort-merge-join-bytes` and
`--late-materialization` are persistent flags that every command's `--help`
prints. On `query`, `shell`, `mcp`, `create-table`, `drop-table` and the
standalone server's PostgreSQL-wire fallback database they were accepted and
ignored. They apply now, exactly as they do to `serve`:

```
wadjet query --memory-budget=4096 "SELECT COUNT(*) FROM big1 CROSS JOIN big2"
```

refuses with `memory budget exceeded` where it used to answer, and
`--spill-dir=D` creates `D/wadjet-spill` where it used to leave `D` untouched.
Because a field nobody sets is the zero value, `--late-materialization`'s
documented default of `true` was running as `false` on those doors; that is
fixed by the same change. (#1226)

### Planner configuration belongs to the database

`wadjet.Config.BushyJoinReorder` is now that database's own setting. Two
`wadjet.DB`s open in one process plan by their own values, and closing one
takes its value with it. It used to be a package-level flag: the first
database in a process that asked for the bushy join regime enabled it for
every other database in that process, and for the rest of the process's life,
whatever their own configuration said. A database configured with the regime
OFF planned bushy join orders, and one opened after a bushy database had
already been closed planned them too. (#1223)

`wadjetd serve --bushy-join-reorder` configures the planners of the process it
is given to: the coordinator's, the HTTP server's and the wire door's fallback
database. A worker that re-plans a whole query from its text plans it under
the setting of the COORDINATOR that dispatched it, which rides the task —
the coordinator chose that task's probe split and build sides from a plan made
under its own setting, and two processes planning one statement two ways
divide a relation the other does not probe.

### Reference

- 387 built-in scalar functions and 29 aggregates.
- Every deliberate divergence from PostgreSQL is listed on the
  [differences page](../postgres-differences.md) and in ADR-0012.
- ADR-0039 records that a table function in `FROM` is a relation and why a
  signature-declared column list is refused at plan time while a reader's is
  refused at its first batch; ADR-0040 records that a resolved setting belongs
  to the instance that uses it and rides the task to a process that re-plans.
