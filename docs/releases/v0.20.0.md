## v0.20.0

Two binaries and two licenses, and a correctness release underneath them: the
embedded engine and the `wadjet` binary are now MIT, the distributed engine
and the new `wadjetd` binary stay AGPL-3.0, and forty issues close across the
planner, the executor and the wire — joins and derived tables publishing the
columns the query wrote, correlated subqueries and `LATERAL` bodies answering
the rows PostgreSQL answers, numbers keeping their digits and declaring their
types, `QUALIFY`, and the network types reading one grammar at every boundary.

### Licensing: MIT engine, AGPL cluster

Wadjet is one repository and one Go module with two licenses. Everything that
answers a query in one process is **MIT**: the parser, the optimizer, the
vectorized executor, the local pipeline planner, the Parquet and Iceberg
readers, the type system, the network functions, the PostgreSQL wire protocol,
the MCP server, and the object-store and catalog layers. What makes a cluster
is **AGPL-3.0**, with a commercial license available: the coordinator, the
workers, the shuffle and gather exchange, and the stage-DAG planner that
decides which machine does what.

- `LICENSING.md` is the map. It names every AGPL directory, the two binaries,
  the commercial option, and the CLA clause the relicensing rests on.
- The root `LICENSE` is the MIT text; `LICENSE-AGPL-3.0` sits beside it, and
  every AGPL directory carries its own copy so a package's license is visible
  where the package is.
- Every `.go` file carries an SPDX header naming its region.
- The boundary is held by a gate, not a promise. `go run ./tools/licensecheck .`
  runs in CI and in `task housekeeping`, and fails if an MIT package reaches
  AGPL code through a non-test import at any depth, if a file's header does
  not match its directory, if an AGPL directory lacks its license text, or if
  the distributed planner's vocabulary — a stage, an exchange, a distribution
  property — is declared under an MIT directory.

### Two binaries

- **`wadjet`** is the engine, the command line, and a new embedded server:
  `wadjet serve` speaks the PostgreSQL wire protocol over the engine in its own
  process, with no task queues, no workers and no coordinator. The catalog's
  key-value store still runs on an embedded NATS server bound to `127.0.0.1`.
  `query`, `shell`, `tables`, `create-table`, `drop-table`, `compact`,
  `catalog`, `clusters` and `mcp` are all here.
- **`wadjetd`** is the distributed server: `serve --mode=standalone`,
  `--mode=coordinator` and `--mode=worker` exactly as before, and the same
  command line, because an operator needs the same tools.
- `task build` builds both into `dist/`; a release publishes both.
- **Upgrading.** `wadjet serve --mode=standalone|coordinator|worker` is now
  `wadjetd serve --mode=...` with the same flags and the same behaviour.
  `wadjet serve` refuses a distributed mode by name and points at `wadjetd`.
  A Go program that embeds `wadjet.DB` is unaffected.

### The embedded engine plans only what it runs

The local planner used to build a stage DAG for every query and then not run
it in a single process. It no longer does, and two things are visible:

- `EXPLAIN VERBOSE` on `wadjet` prints the pipeline it executes and names no
  stage. On `wadjetd`, `EXPLAIN` is routed to the coordinator so that the
  PostgreSQL wire door and the HTTP door print the same plan: the stage DAG
  the coordinator would dispatch, exchanges included. `EXPLAIN ANALYZE` is
  unchanged.
- The query cost guard estimates from the logical plan rather than from a
  stage list, on both binaries, so a query is refused or answered by its own
  text and not by which server received it.

### Joins and derived tables publish the columns the query wrote

- **`SELECT *` over a join publishes the `FROM` clause's arms in written
  order**, one column per source column, duplicate names kept by position, on
  every execution path and on the wire. The column order and the qualified
  names no longer follow the cost model's join reordering or which side became
  the hash-join build side, so the same statement declares the same
  `RowDescription` under any predicate and any data size.
- **A derived table, a CTE or a `LATERAL` block publishes exactly its visible
  projection.** A qualified star over a block with an unaliased expression
  (`SELECT x.* FROM (SELECT id, g + 1 FROM t) x`) answers the value under
  `?column?` rather than `NULL` under a string. A block's own `ORDER BY …
  LIMIT` no longer leaks its materialized sort key (`__sortkey_0`) to the
  client, and a grouped `LATERAL` no longer leaks its correlation slot
  (`__key_0`) on the distributed paths — a slot an operator mints is dropped
  by the operator that minted it.
- **The second sort key over a derived self-join is applied**, and an output
  alias that equals a source column's name no longer captures the group key.
- **A set-operation arm, a join-bodied derived arm, a grouped arm and a nested
  renamed arm are named and keyed on the distributed paths as on the single
  path.** A qualified reference into a `UNION` arm binds that arm's column;
  `DISTINCT` over a join with a join-bodied arm no longer returns rows that
  violate the join condition; an outer join over such an arm pads with `NULL`
  where it padded with a value.

### Correlated subqueries answer the rows PostgreSQL answers

- **`IN` and `EXISTS` on the outer relation of a join no longer lose rows.**
  The probe key of a decorrelated semi- or anti-join was spelled bare and
  could bind the other join arm's column of the same name.
- **A correlated `EXISTS` whose body declares its own `WITH`** answers the
  matching rows rather than none; the body's CTEs are in scope for the body.
- **A `JOIN` keyed on a recursive CTE's column** answers the matching rows
  rather than the cross product; a recursive CTE reference publishes its
  column list, and an alias list that does not match the body's width is
  refused with PostgreSQL's `42P10`.
- **A set operation nested inside a correlated body** is refused with `0A000`
  naming the shape, where it silently answered `NULL` for every outer row.
- **An uncorrelated `LATERAL` whose body aggregates over a CTE** answers the
  aggregate rather than the outer row's own value.
- **`QUALIFY`** filters the rows a window function produced, the way `HAVING`
  filters a `GROUP BY`. PostgreSQL has no such clause; wadjet implements the
  one DuckDB, Snowflake and BigQuery define, and DuckDB is recorded as the
  oracle for it. The clause used to be parsed and ignored.

### Numbers keep their digits and declare their types

- **A `FLOAT64` result outside the type is `22003`, not an infinity.**
  `1e308 * 10`, `1e308 + 1e308`, `1e308 / 0.5`, and a `SUM` or `AVG` whose
  running total leaves the type are refused as PostgreSQL refuses them, and a
  `CREATE TABLE … AS SELECT` over one no longer stores the infinity. A column
  that holds an infinity or a NaN is unaffected. The float arithmetic kernels
  carry the check inside their loops and run about a fifth faster than they did before this release.
- **`SUM` over a `REAL` column accumulates at `real`'s width**, in the grouped
  and windowed spellings alike, and declares `real` on the wire. Arithmetic
  over two `REAL` operands computes at `real`'s width too:
  `r + CAST(1.0 AS REAL)` over 2^24 answers 16777216. A moving window frame
  (`ROWS BETWEEN n PRECEDING …`) over a `REAL` or `FLOAT64` column recomputes
  each frame rather than subtracting the departing row, which is what
  PostgreSQL does for float sums.
- **A wide `DECIMAL` literal under a cast keeps every digit it was written
  with**, and a bare wide integer literal declares `bigint` or `numeric` as
  PostgreSQL does rather than rounding through a double.
- **`PARSE_BYTES`, `PARSE_RATE`, `HUMAN_READABLE_SECONDS` and `FROM_UNIXTIME`**
  read an integer argument exactly.
- **Declared types follow PostgreSQL's.** `MIN` and `MAX` over `integer` declare
  `integer`; a window aggregate over an integer input, a set operation or a
  `ROW` field declares the integer type rather than `float8`; the bitwise
  functions follow their operands' width; an integer literal in a scalar
  subquery declares `integer`; and an `ARRAY` column declares its element's
  array type on the wire (`integer[]`, `text[]`, `numeric[]`, `uuid[]`, …)
  in both formats and in `Describe`, so a typed client reads an array as one.

### Network types: one grammar at every boundary

Each of `IPV4`, `IPV6`, `CIDR`, `MAC`, `UUID`, `PORT` and `PROTOCOL` has one
text grammar, measured against PostgreSQL 17.11's `inet`, `macaddr` and `uuid`
input functions cell by cell, and it is the grammar at every boundary: the
writer (`INSERT`, `COPY`, the embedded ingester), the query-time `CAST`, a
literal at plan time, and a literal assigned into a typed column.

- **`CAST(col AS IPV4)` parses.** It used to pass a string through unchanged
  under a network declaration. A string column from a Parquet, CSV or JSON
  file written by another tool can now become a native column with one
  `CREATE TABLE … AS SELECT CAST(…)`, and the result round-trips through the
  writer and the catalog. The ingestion guide's Bento section now describes
  that path and the in-process ingester rather than a hand-off through
  untyped files.
- **Every form PostgreSQL accepts is accepted**, and every form it rejects is
  `22P02` naming the text: abbreviated addresses (`192.168`, `10/8`), leading
  zeros, one trailing dot, all seven `macaddr` notations, braced and no-dash
  UUIDs in any case. A malformed literal in a `WHERE` clause is refused at
  plan time, over an empty table as over a full one.
- **`CAST('udp' AS PROTOCOL)`** accepts the IANA name, case-insensitively, so
  a `PROTOCOL` round-trips through its own text form.
- **`INSERT INTO t (ip) SELECT '10.0.0.1'`** resolves the literal against the
  target column, as `INSERT … VALUES` always did.
- **A `PORT` or `PROTOCOL` value is range-checked where it enters the type**,
  by cast or by write: `CAST(70000 AS PORT)` is `22003`, and so is writing
  70000 into a `PORT` column by any door. Arithmetic over a port is integer
  arithmetic and may leave the range without error, as `smallint + 1` does
  in PostgreSQL; the result is an integer, not a port.
