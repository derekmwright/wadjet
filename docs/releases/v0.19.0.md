## v0.19.0

A feature release: time bucketing and OHLCV bars, TCP flag functions over
exact 64-bit arithmetic, a semantic-version family, ROW-returning scalar
functions that work in every SQL position, and a run of scope repairs that let
`LATERAL`, recursive CTEs and correlated scalar subqueries answer where they
previously returned nothing or the wrong thing.

### Downsampling: `TIME_BUCKET` and `OHLCV`

These landed in v0.18.67 and were not described in that release's notes; they
are new to anyone upgrading from v0.18.66 and already present for anyone on
v0.18.67 or later.

- **`TIME_BUCKET(stride, ts[, origin])`** — floor a timestamp to a fixed-width
  bucket, PostgreSQL's `date_bin` semantics digit for digit. Buckets are UTC
  and exactly `stride` wide; the origin defaults to `1970-01-01`. It returns a
  TIMESTAMP, so a client reads it as one. A stride containing months or years
  is refused (it has no fixed width), as is a stride of zero or less.
- **`OHLCV(ts, price, volume)`** — one aggregate that answers a whole bar as a
  ROW `(open, high, low, close, volume, vwap)`. It is general-purpose
  downsampling: latency, sensor readings, flow bytes, not only prices.

  ```sql
  SELECT bucket, (bar).open, (bar).close, (bar).vwap
  FROM (SELECT TIME_BUCKET(INTERVAL '5' MINUTE, ts) AS bucket,
               OHLCV(ts, price, size) AS bar
        FROM trades GROUP BY 1) t
  ORDER BY bucket;
  ```

  Rows sharing an instant are ordered by price, so a bar does not depend on how
  the query was executed. A row with any NULL argument is skipped, and a group
  with no remaining rows answers a NULL bar. `vwap` is the exact weighted mean
  of the price and carries `AVG(price)`'s type.
- Bars are computed in pieces and combined, so a distributed `OHLCV` ships one
  small state per group instead of every row.
- **A ROW column renders in its declared field order on every path.** A
  composite produced by an aggregate previously rendered with its fields sorted
  by name.
- **An aggregate with no window form is refused with a clear message** naming
  the sixteen window functions, instead of failing the query with an internal
  error. `STDDEV`, `MEDIAN`, `STRING_AGG`, `MIN_BY`, `CORR` and eighteen others
  are affected.
- **A sub-day interval unit the INTERVAL type cannot hold is refused, not
  silently scaled as days.** `INTERVAL '500' MILLISECOND` — and MICROSECOND,
  and the other fields the type does not carry — used to compile to 500 DAYS;
  it is now an error naming the unit, pending sub-day interval support (#1005).

### TCP flags, and bitwise arithmetic that is exact

- **TCP flag functions.** `TCP_FLAGS_HAS_ALL`, `TCP_FLAGS_HAS_ANY`,
  `TCP_FLAGS_HAS_NONE`, `TCP_FLAG_MASK`, `TCP_FLAGS` and `TCP_FLAGS_TEXT` read
  an integer flags column against the nine bit names RFC 9293 defines (FIN,
  SYN, RST, PSH, ACK, URG, ECE, CWR, AE; `NS` is accepted for `AE`). They are
  PostgreSQL's `(flags & mask) = mask` / `<> 0` / `= 0` under readable names.
  Names fold case and NULL flags give NULL. A name the table does not know is
  SQLSTATE `22023` naming it — before the query is planned, on every execution
  path and in every expression position, including a query that selects no rows
  — never a quietly smaller mask. A name supplied by a column is checked per
  row. This holds inside a scalar subquery placed in `ORDER BY`, `GROUP BY` or
  a window function's argument, and inside a recursive CTE's body. A flags
  argument that is not an integer is `22023` naming the type it was given.
- **Flag predicates are evaluated inside the scan.** A `TCP_FLAGS_HAS_*`
  predicate over a bare column with literal names — and the
  `BITWISE_AND(flags, 18) = 18` spelling of the same test — is answered by the
  scan: once per dictionary entry on a dictionary-encoded column, and a flags
  column referenced only by the filter is never materialized. Disable with
  `WADJET_FLAG_DICT_PUSHDOWN=0`.
- **The bitwise functions are exact and answer integers.**
  `BITWISE_AND/OR/XOR/NOT`, the three shifts, `TO_HEX`, `TO_BASE`,
  `BIT_COUNT`, `FROM_HEX` and `FROM_BASE` read their arguments as 64-bit
  patterns instead of through a double, so values above 2^53 keep their low
  bits: `BITWISE_AND(4611686018427387922, 18)` is 18, not 0. `TO_HEX` renders
  PostgreSQL's two's complement. `FROM_HEX` requires the whole string:
  `FROM_HEX('12zz')` is NULL, as `FROM_BASE('12zz', 16)` has always been.
- **`SUM` over a function declares what PostgreSQL declares.**
  `SUM(LENGTH(s))`, `SUM(REGEXP_COUNT(s,'a'))`, `SUM(PREFIX_LENGTH(c))` and
  `SUM(PAYLOAD_LENGTH(p))` are `bigint`; `SUM(BIT_COUNT(x))`,
  `SUM(FROM_HEX(s))` and `SUM(PARSE_BYTES(s))` are `numeric`, so a wide total
  answers instead of overflowing. The bitwise functions follow their operands:
  `SUM(BITWISE_AND(int_col, 18))` is `bigint` and
  `SUM(BITWISE_AND(bigint_col, 18))` is `numeric`. The grouped and the windowed
  spelling agree.
- **An integer's PostgreSQL width survives a derived table, a CTE, a set
  operation and a window slot.** `SELECT SUM(v) FROM (SELECT BITWISE_AND(id,3)
  AS v FROM flows) s` declares `bigint`, exactly as the direct
  `SUM(BITWISE_AND(id,3))` does; the same for `REGEXP_COUNT`, arithmetic, a
  `UNION ALL` of int4 arms and `SUM(v) OVER ()`. A set operation with one
  `bigint` arm is `numeric`, PostgreSQL's common-type rule.
- **`MIN` and `MAX` over a computed integer expression declare the
  expression's own type.** `SELECT SUM(m) FROM (SELECT MIN(BITWISE_AND(a,3))
  AS m FROM t) s` is `bigint` and the `bigint` column's form is `numeric`,
  grouped and `OVER ()`. The windowed form previously declared
  `double precision`.
- **A scalar subquery's column keeps its type through a derived table, a CTE or
  a window slot.** `SELECT SUM(v) FROM (SELECT (SELECT BITWISE_AND(a,3) FROM
  u) AS v FROM t) s` is `bigint` where it was `double precision`; the `bigint` and
  `COUNT(*)` forms are `numeric`. Written directly as an aggregate's argument —
  `SUM((SELECT …))` — it is exact too: `SUM((SELECT CAST(9007199254740993 AS
  BIGINT)))` over three rows is `27021597764222979` as `numeric`, where it was
  a rounded `double precision`.
- **A window function over a computed column of a derived table answers on
  distributed queries.** `SELECT SUM(v) OVER () FROM (SELECT BITWISE_AND(a,b)
  AS v FROM t) s` returned NULL in every row when the query ran as a stage DAG,
  and the correct value when it ran in one process.
- **The legacy TCP inspection functions read the ninth bit and refuse a name
  they do not know.** `TCP_FLAGS_TO_STRING(256)` named no flag at all and names
  `AE`; `HAS_TCP_FLAG(f,'AE')` answered NULL and answers;
  `TCP_FLAGS_FROM_STRING('SYN,ACKK')` answered 2 — a silently smaller mask —
  and is now an error naming `ACKK`. All five refuse a flags argument that is
  not an integer.

### Semantic versions

- **`SEMVER_VALID`, `SEMVER_MAJOR`, `SEMVER_MINOR`, `SEMVER_PATCH`,
  `SEMVER_PRERELEASE`, `SEMVER_BUILD`, `SEMVER_CMP`, `SEMVER_SORT_KEY`,
  `SEMVER_NORMALIZE`, `SEMVER_NORMALIZE_STRICT` and `SEMVER_SATISFIES`** give a
  version string the ordering Semantic Versioning 2.0.0 defines. There is no
  new type: `SEMVER_SORT_KEY(v)` is text whose byte order is precedence, so
  `ORDER BY`, `MIN`/`MAX`, a distributed merge and a spilled sort order
  versions correctly as they are.
- A string that is not a version is NULL from every function but
  `SEMVER_VALID`, which answers `false`, and the strict forms, which raise
  SQLSTATE `22023` naming it. A leading `v` is accepted.
- **`SEMVER_SATISFIES(v, range)`** implements node-semver's range grammar —
  `^1.2.3`, `~1.2`, `>=1.2.0 <2.0.0`, `1.2.x`, `*`, `1.2.3 - 2.3`, `||` — with
  node's pre-release rule. A range spelling the grammar does not know is
  `22023` naming it, before any row when it is a literal, never a silent
  `false`. A bound at the top of the `BIGINT` domain saturates instead of
  wrapping, and a `>=0.0.0` comparator is dropped from a set the way
  node-semver drops it, so a range that opts into the pre-releases of `0.0.0`
  (Go pseudo-versions, for one) answers what node answers.
- `SEMVER_CMP` declares `integer` and the three components `bigint`; the family
  answers identically on every execution arm and both wire encodings.
- **A per-row data refusal no longer retries.** A `22023` raised inside a worker
  task is deterministic, so the distributed path reports it on the first
  attempt instead of spending the retry budget on it; transient failures keep
  their retries.

### ROW-returning functions

- **A scalar function that returns a fixed-schema ROW keeps its fields through
  every SQL position** — `DISTINCT`, `GROUP BY`, `UNION` / `INTERSECT` /
  `EXCEPT`, a bare `NULL` arm, window keys, hidden sort keys and the
  distributed stage boundary — where before the distributed path could answer
  NULL for the composite. A ROW field path read through a derived table groups
  correctly on the distributed path.
- **`SEMVER_PARSE(s)` and `SEMVER_PARSE_STRICT(s)`** return the version as a
  ROW `(major, minor, patch, prerelease, build)` whose fields equal the
  component functions; the strict form is `22023` naming the string.
- A field of a call can be read directly, `(SEMVER_PARSE(v)).major`, without an
  alias; a field path over anything that is not a ROW is SQLSTATE `42809`
  naming the type, as PostgreSQL answers it.
- ARRAY- and MAP-returning scalars keep their previous behaviour (#1017 stays
  open for them).

### Scalar subqueries with no `FROM` clause

- **A scalar subquery with no `FROM` clause is its `SELECT` expression,**
  evaluated in the enclosing query's scope: `SELECT (SELECT u.x) FROM (SELECT
  id AS x FROM t) u` answers the row's `x` instead of an empty value, at the
  type and under the column name PostgreSQL gives it (`(SELECT 1 AS zzz)`
  publishes `zzz`). It works over a derived table, a CTE, a set-operation body,
  a column-alias list and a base-table alias, in the `SELECT` list and in
  `WHERE` and `HAVING`, and the stage DAG executes it rather than falling back
  to the coordinator.
- A correlated subquery's per-row re-run substitutes the outer row into its
  `SELECT` list and `HAVING` as well as its `WHERE`, and the correlation walk
  reads every clause of the body, a `JOIN`'s `ON`, and every set-operation arm.
  A body the re-run cannot rewrite — a set operation, an aggregate beside a
  nested subquery that itself reads the outer row, or a term that would render
  as a bare ordinal — is SQLSTATE `0A000` naming it, never a silently wrong
  row.
- `GROUP BY (SELECT 1)` raises PostgreSQL's `42803` instead of grouping by an
  ordinal; a scalar subquery in `GROUP BY` that names an ungrouped outer column
  raises `42803` as PostgreSQL does; and an outer column named only in
  `GROUP BY`, `ORDER BY` or a `JOIN`'s `ON` is carried into the outer
  projection the way one named in `WHERE` always was. `SELECT *` with no
  relation is `42601`, and `ORDER BY (SELECT 1)` is a constant sort, not an
  ordinal.
- **A window function inside a correlated subquery is refused** with `0A000`
  and a sentence naming the correlation, instead of silently answering one
  constant for every outer row. Compute the window outside the subquery, or
  make the subquery uncorrelated; an uncorrelated subquery's window is
  unaffected (#1045 stays open for execution).

### `LATERAL` and recursive CTEs

- **A `LATERAL` subquery with no `FROM` clause** — `FROM users u, LATERAL
  (SELECT u.id AS v) l` — answers the outer row's values under the outer
  column's declared type. It previously returned NULL for every such column,
  declared as text. It declares the column's own type over a derived table, a
  CTE or a sorted block, not just over a table.
- A `LATERAL` body that reads the outer row and cannot be computed as a
  projection over it (an aggregate, a `GROUP BY`, a `HAVING`, a `QUALIFY`, a
  window function, `DISTINCT`, a `LIMIT`, a set operation, a `WITH`, a star, or
  a subquery in its select list), and an outer join over one whose `ON` does
  not fold to true, are refused with SQLSTATE `0A000` naming the reason. An
  `ORDER BY` over such a one-row body is the identity and is simply dropped. A
  literal or an ordinal in a window's `PARTITION BY` or `ORDER BY` is not a
  read of the outer row; a window function whose argument reads the outer row
  is refused rather than answering NULL.
- A `LATERAL` body with no `FROM` clause that reads no outer column keeps
  answering exactly as before — `LATERAL (SELECT 7 AS v LIMIT 1)`,
  `(SELECT DISTINCT 7 AS v)`, `(SELECT COUNT(*) AS c)`,
  `(SELECT ROW_NUMBER() OVER () AS v)` and the rest. Only a body that reads the
  outer row is computed as a projection, and only such a body is refused when
  it cannot be.
- **A `LATERAL` FROM item's column-alias list** — `LATERAL (SELECT u.id AS v)
  l(w)` — renames the body's columns; a list longer than the body is SQLSTATE
  `42P10`. Over a `SELECT *` body the list is honoured as PostgreSQL honours it
  when nothing reads the renamed columns, and refused with `0A000` naming the
  star when the query reads a name the list introduces — in a `SELECT` item, a
  filter, an aggregate, a window, a sibling lateral or an `ORDER BY` — rather
  than silently answering NULL for it or sorting by nothing. A bare output
  alias standing alone as a sort term binds to the output column, as in
  PostgreSQL; the same name inside a sort expression is a read of the lateral's
  column.
- **A `WITH RECURSIVE` written inside a derived table, inside another CTE's
  body, inside a `LATERAL` or in a set-operation arm answers its rows.** It
  previously returned zero rows. Two sibling blocks may declare recursive CTEs
  of the same name without reading each other's rows, and reading a recursive
  CTE that cannot be materialized is an error naming the CTE rather than an
  empty result.
- **A recursive CTE written with `UNION` rather than `UNION ALL` is refused**
  with `0A000` naming the spelling. It previously did not terminate: the
  planner re-entered the CTE's own materialization until the process ran out of
  memory.
- **A `WITH RECURSIVE` body's form is read from its parsed set-operation
  tree** the way PostgreSQL reads it: the last `UNION ALL` arm is the recursive
  term and every arm before it is the non-recursive term, so a three-arm body
  such as `SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT v+1 FROM r …` answers
  PostgreSQL's rows. A self-reference in any earlier arm, or a body with no set
  operation, is SQLSTATE `42P19` with PostgreSQL's own message.
- A `WITH RECURSIVE` whose body does not name itself is answered as the
  ordinary query it is, including a plain `UNION` between its arms; and a
  `UNION ALL` whose second arm names no CTE answers its two rows instead of
  repeating the second arm a thousand times.

### Set operations, sorts and group keys on the distributed paths

- A `GROUP BY` or `SELECT DISTINCT` over a nullable `STRING` or `BYTES` column
  no longer loses its NULL group on a distributed worker running fragments in
  parallel. The NULL rows were counted into another group, dropped, or — where
  the NULL arrived first — the query failed. Every other key type was
  unaffected.
- A set operation's ordinal `ORDER BY` terms address its result columns. Where
  two of those columns share a name, `SELECT a AS x, b FROM t UNION SELECT c, d
  FROM u ORDER BY 1, 2 DESC` previously applied only the first key, and on the
  distributed paths the operation also deduplicated on the wrong tuple: a
  `UNION` returned fewer rows than it should with the second column carrying
  the first's values, and `INTERSECT` and `EXCEPT` returned none.
- `ORDER BY <n>` at or past a `SELECT *` in a set operation's first arm is
  answered instead of refused with `ORDER BY position N is out of range (1-1)`.
- A chain of three or more set operations whose result columns share a name is
  answered on the distributed paths instead of failing the query with a
  column-type disagreement between the operation's own output files.
- A qualified `ORDER BY` term beside an output column of the same name —
  `ORDER BY 1, b.amount DESC` where the select list publishes `amount` twice —
  binds the column its qualifier names on the distributed paths as well as in
  process.

### Repository cleanup

- No behaviour change: nine plan-dump and trace harnesses that asserted
  nothing, an SF10 stall repro for a family closed in August, and three one-off
  perf probe binaries (`s3probe`, `spilltest`, `plan-repro`) are removed, and
  nine query-numbered regression tests are renamed for the mechanism they pin.
  `refault-probe` stays as the page-cache sensor's field diagnostic.

### Comment reorganisation

- No behaviour change: across `internal/` and the public `wadjet/` package,
  every comment block longer than twenty lines that existed at the previous
  release is cut to its invariant, boundary and pointers, and the 643 design
  essays they carried move verbatim to `docs/internals/`. Comment lines in
  production Go fall from 92,120 to 81,266. No declaration changed in the
  comment pass itself: 220 file revisions compared parent-to-commit, none
  differ once comments are stripped.
