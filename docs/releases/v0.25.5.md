## v0.25.5

A patch release for correctness and PostgreSQL compatibility. It covers regular-expression pattern syntax, unconstrained NUMERIC columns, GROUP BY key matching, float rounding, per-value numeric display scale and declared output types. **The first section lists what a client or a stored query sees differently after the upgrade.**

### Behaviour changes

**New refusals and error codes.**

- `SELECT regexp_like('a', '(')` now raises `2201B`; v0.25.4 answered NULL. `regexp_count` and `substring(s FROM p)` refuse an invalid pattern the same way.
- `SELECT regexp_like('abab', '(a)b\1')` now raises `0A000`, where v0.25.4 answered NULL and PostgreSQL answers `t` ([text-collation r3](../adr/0012-divergences/text-collation.md)).
- `CREATE TABLE t (v NUMERIC); INSERT INTO t VALUES (12345678901234567890123456789)` now raises `22003`; v0.25.4 stored the value ([numeric-decimal r23](../adr/0012-divergences/numeric-decimal.md)).
- Over a `NUMERIC` column holding 1234567890, `SELECT v * v FROM t` now raises `22003`, where v0.25.4 answered 1524157875019052100; `CAST(v AS NUMERIC(38,0)) * v` answers 1524157875019052100.0000000000 ([numeric-decimal r17](../adr/0012-divergences/numeric-decimal.md)).
- Over a DOUBLE PRECISION 2.5, `SELECT round(f, 400) FROM t` now raises `22003`; v0.25.4 answered NaN.
- `SELECT (SELECT max(x.v) FROM ss_i x WHERE x.v > t.i) FROM ss_t t GROUP BY t.g` now raises `42803` with PostgreSQL's `subquery uses ungrouped column "t.i" from outer query`; v0.25.4 raised `42703`.

**Declared types and stored values.**

- `CREATE TABLE t (v NUMERIC); INSERT INTO t VALUES (1.25); SELECT v FROM t` now reads 1.25 and declares numeric with no type modifier; v0.25.4 read 1 and declared numeric(38,0). `DECIMAL` behaves the same.
- For that column, `information_schema.columns` now reports `numeric_precision` and `numeric_scale` NULL, where v0.25.4 reported 38 and 0.
- A `NUMERIC` column now stores 10 fraction digits: `INSERT INTO t VALUES (0.00000000005)` stores 0.0000000001, where v0.25.4 stored 0, and `UPDATE t SET v = v / 3` over 10 stores 3.3333333333, where v0.25.4 stored 3.
- `CREATE TABLE c AS SELECT CAST(NULL AS NUMERIC) AS v`, alone or `UNION ALL SELECT 2`, now creates a numeric column where v0.25.4 created double precision.
- A table created by v0.25.4 keeps its declaration: after the upgrade, `INSERT INTO t VALUES (2.75)` into a v0.25.4 `NUMERIC` column still reads 3.
- Over a DOUBLE PRECISION 0.25, `SELECT round(f, 1)` now answers 0.2, where v0.25.4 answered 0.3; PostgreSQL raises `42883` ([numeric-decimal r22](../adr/0012-divergences/numeric-decimal.md)).
- A column CREATE TABLE AS made by v0.25.4 from an expression PostgreSQL types numeric (`5 / 2.0 + id * 0`) records no category: after the upgrade `round(b)` over its 2.5 answers 2, where v0.25.4 answered 3. Create the table again to record the category.
- With `n NUMERIC(10,2)`, `SELECT 2 * t.n, COUNT(*) FROM ss_t t GROUP BY 2 * n` now declares numeric (OID 1700) instead of text (OID 25).
- `CREATE TABLE c AS SELECT 2 * t.n AS k, COUNT(*) AS c FROM ss_t t GROUP BY 2 * n` now creates a numeric column that reads `-7, 0.02, 4.5, 20` in order; v0.25.4 created a text column that read `-7.00, 0.02, 20.00, 4.50`. PostgreSQL reads `-7.00, 0.02, 4.50, 20.00` ([numeric-decimal r24](../adr/0012-divergences/numeric-decimal.md)).
- `SELECT sum(q.v) FROM (SELECT f + a.i AS v FROM ss_t a GROUP BY f + a.i) q` over a double `f` and integer `i` now declares double precision (OID 701) instead of bigint (OID 20); `SELECT sum(q.i) FROM (SELECT f AS i FROM ss_t) q` the same.
- `SELECT d.x + 1 AS k, count(*) FROM ss_t t LEFT JOIN (SELECT id, v AS x FROM ss_i) d ON d.id = t.id GROUP BY d.x + 1` over an integer `v` now declares bigint (OID 20) instead of double precision (OID 701).

**Printed text.**

- `CREATE TABLE t AS SELECT 2.50 AS v; SELECT v FROM t` now declares numeric with no type modifier and prints 2.5; v0.25.4 declared numeric(3,2) and printed 2.50, as PostgreSQL does ([numeric-decimal r24](../adr/0012-divergences/numeric-decimal.md)).
- Over a numeric(15,2) column holding 12.75, NULL, 1.00 and -3.50, `SELECT COALESCE(n, 12.3456789012345) FROM t` now prints `12.75, 12.3456789012345, 1.00, -3.50`; v0.25.4 printed every value at 13 fraction digits.
- Over that column, `COALESCE(n, '7')`, `COALESCE(n, 14)` and `LEAST(n, '0.5')` now print `7`, `14` and `0.5`, where v0.25.4 printed `7.00`, `14.00` and `0.50`.
- Over that column, `SELECT n FROM t WHERE id IN (1, 3) UNION ALL SELECT 2.5 UNION ALL SELECT 7 ORDER BY 1` now prints `1.00, 2.5, 7, 12.75`; v0.25.4 printed `1.00, 2.50, 7.00, 12.75`. A text predicate over such a result counts differently: `CAST(n AS TEXT) LIKE '%0'` over the non-NULL rows and `2.5` now counts 2, where v0.25.4 counted 3.

**Work and storage.** A query planned for the stage DAG that rounds a column whose numeric category a stage boundary would drop now runs on the coordinator's local path instead. A `.wshf` exchange file marks an unconstrained DECIMAL column in bit 7 of its precision byte, and a DECIMAL column whose values print at a scale other than the carrier's carries a display-scale section: two bytes when every value shares one scale, a code per row otherwise ([ADR-0010](../adr/0010-shuffle-wire-formats.md)); spill runs carry the same section.

### PostgreSQL's regular-expression constructs read PostgreSQL's pattern syntax

`regexp_like`, `regexp_count`, `substring(s FROM p)` and SIMILAR TO handed their pattern to RE2 untranslated. `SELECT regexp_like('abc', '\b'), regexp_count('abc', '\b')` now answers `f, 0`, as PostgreSQL does (`\b` is a backspace there; the word boundary is `\y`); v0.25.4 answered `t, 2`. `SELECT substring('abc' FROM 'a|ab')` now answers `ab` and `SELECT E'a\nc' SIMILAR TO 'a_c'` answers `t`; v0.25.4 answered `a` and `f`. An invalid pattern now raises `2201B` in `regexp_like`, `regexp_count` and `substring(s FROM p)`: `SELECT regexp_like('a', '(')` answered NULL at v0.25.4. `SELECT regexp_like('ABC', 'abc', 'i')` now answers `t` and `SELECT regexp_count('abcabc', 'a', 2)` answers 1; v0.25.4 raised `42883` for both. `regexp_replace` now takes the flags `n`, `m`, `p`, `w` and `x`: `SELECT regexp_replace(E'x\nab', '^a', 'X', 'n')` answers `x` and `Xb` on two lines, where v0.25.4 raised `0A000`. The engine's own `regexp_extract`, `regexp_extract_all`, `regexp_split` and `payload_matches` keep RE2 syntax, as DuckDB reads them: `SELECT regexp_extract('the cat sat', '\bcat\b')` answers `cat` in both versions. A back reference is refused in every PostgreSQL construct ([text-collation r3](../adr/0012-divergences/text-collation.md)), the flags `b` and `e` stay refused ([text-collation r23](../adr/0012-divergences/text-collation.md)), and `SELECT regexp_count('ab', '\yb', 2)` raises `0A000` where PostgreSQL answers 0 ([text-collation r25](../adr/0012-divergences/text-collation.md)). (#1499)

### A column created from an unconstrained NUMERIC

A column declared `NUMERIC` or `DECIMAL` without a precision, and a CREATE TABLE AS column whose source is plain numeric, was created as numeric(38,0), or as double precision from a typed NULL. `CREATE TABLE t (v NUMERIC); INSERT INTO t VALUES (1.25); SELECT v FROM t` now reads 1.25 and declares numeric with no type modifier; v0.25.4 read 1 and declared numeric(38,0). `CREATE TABLE c AS SELECT CAST(1 AS NUMERIC) AS v; INSERT INTO c VALUES (1.25)` now reads `1, 1.25`, where v0.25.4 read `1, 1`, and `CREATE TABLE c AS SELECT CAST(NULL AS NUMERIC) AS v`, alone or `UNION ALL SELECT 2`, now creates a numeric column where v0.25.4 created double precision. The column holds 10 fraction digits and 28 integer digits: `INSERT INTO t VALUES (0.00000000005)` stores 0.0000000001 and a 29-digit integer raises `22003`, where PostgreSQL stores both ([numeric-decimal r23](../adr/0012-divergences/numeric-decimal.md)). A stored value prints without trailing zeros, so `CREATE TABLE t AS SELECT 2.50 AS v; SELECT v FROM t` prints 2.5 where PostgreSQL prints 2.50 ([numeric-decimal r24](../adr/0012-divergences/numeric-decimal.md)). A table created by v0.25.4 keeps its declaration: after the upgrade, `INSERT INTO t VALUES (2.75)` into a v0.25.4 `NUMERIC` column still reads 3. (#1541)

### A GROUP BY key is matched by the column it names

The binder now records which column each reference names, and the group-key match compares those bindings instead of the spelling ([ADR-0047](../adr/0047-a-column-reference-has-one-resolved-identity.md) stage 1). With `n NUMERIC(10,2)` holding 2.25, 10.00, -3.50 and 0.01, `SELECT 2 * t.n, COUNT(*) FROM ss_t t GROUP BY 2 * n ORDER BY 1` now declares numeric and orders `-7.00, 0.02, 4.50, 20.00`; v0.25.4 declared text and ordered `20.00` before `4.50`. The mirror spelling `SELECT 2 * n … GROUP BY 2 * t.n`, and over a join `SELECT i + 1 … FROM ss_t t JOIN ss_i u ON u.id = t.id GROUP BY t.i + 1`, now answer; v0.25.4 raised `42803`. A subquery that reads an ungrouped column of the outer query, `SELECT (SELECT max(x.v) FROM ss_i x WHERE x.v > t.i) FROM ss_t t GROUP BY t.g`, now raises `42803` with PostgreSQL's message; v0.25.4 raised `42703`. Through the coordinator these statements keep their v0.25.4 answers, a designed interim: the stage-DAG arms plan a tree the coordinator does not yet bind ([names-scopes r10](../adr/0012-divergences/names-scopes.md), ADR-0047 stage 5). (#1524 stays open)

### A float rounds by its declared type, and a created column keeps its numeric category

Over a DOUBLE PRECISION column holding 2.5, 0.5 and -2.5, `SELECT round(f) FROM t` now answers `2, 0, -2`, half to even as PostgreSQL rounds a float; v0.25.4 answered `3, 1, -3`. `SELECT CAST(ARRAY[2.5::float8, 1.5::float8] AS BIGINT[])` now answers `{2,2}`; v0.25.4 answered `{3,2}`. A column CREATE TABLE AS makes from an expression PostgreSQL types numeric (`sqrt(6.25 + id * 0)`, `5 / 2.0 + id * 0`) stays double precision here but records that category: over its 2.5, `CAST(b AS INTEGER)`, `b::bigint` and an INSERT … SELECT, UPDATE or MERGE into an integer column now give 3, as PostgreSQL does; v0.25.4 gave 2. A column created by v0.25.4 records no category and reads as double precision after the upgrade: `round(b)` over its 2.5 answers 2, where v0.25.4 answered 3; create the table again to record the category. The double precision declaration of such a column is [dml-assignment r1](../adr/0012-divergences/dml-assignment.md). (#381, #1542)

### A numeric value carries its own display scale

A numeric result printed every value of a column at one scale; a value now carries its own display scale, as PostgreSQL's numeric does ([ADR-0024 §11](../adr/0024-decimal-is-finite-fixed-point-with-postgres-result-types.md)). Over a numeric(15,2) column holding 12.75, NULL, 1.00 and -3.50, `SELECT COALESCE(n, 12.3456789012345) FROM t` now prints `12.75, 12.3456789012345, 1.00, -3.50`; v0.25.4 printed every value at 13 fraction digits (`12.7500000000000`, …, `-3.5000000000000`). `COALESCE(n, '7')`, `COALESCE(n, 14)` and `LEAST(n, '0.5')` now print `7`, `14` and `0.5` where v0.25.4 printed `7.00`, `14.00` and `0.50`. A set operation prints each arm's value at its own scale: `SELECT n FROM t WHERE id IN (1, 3) UNION ALL SELECT 2.5 UNION ALL SELECT 7 ORDER BY 1` now prints `1.00, 2.5, 7, 12.75`, where v0.25.4 printed `1.00, 2.50, 7.00, 12.75`. `2.50` and `2.5` still compare, group and deduplicate as one value: `SELECT count(DISTINCT v) FROM (SELECT 2.50 AS v UNION ALL SELECT 2.5) s` answers 1 in both versions. Arithmetic over values of different display scales, a choice over literals only and numeric array elements keep their v0.25.4 text: `SELECT GREATEST(-2.50, 0.1)` still prints `0.10` where PostgreSQL prints `0.1` ([numeric-decimal r18](../adr/0012-divergences/numeric-decimal.md)). A `.wshf` exchange file whose DECIMAL header carries a precision past 38 or an unknown flag bit is now refused by both header readers and never written. (#1647, #764, #1662)

### A declared output is keyed by the column it names

The declaration walk now declares a bound reference by the input position it names, and no name lookup reads an expression's text as the column after its last dot (ADR-0047 stage 2). With DOUBLE PRECISION `f` holding 4.25 and 96.125 and INTEGER `i` holding 1 and 2, `SELECT sum(q.v) FROM (SELECT f + a.i AS v FROM ss_t a GROUP BY f + a.i) q` now declares double precision and answers 103.375; v0.25.4 declared bigint and answered 103. An aggregate's argument is declared by its binding: `SELECT sum(q.i) FROM (SELECT f AS i FROM ss_t) q` now answers 100.375 as double precision, where v0.25.4 answered bigint 100. `SELECT d.x + 1 AS k, count(*) FROM ss_t t LEFT JOIN (SELECT id, v AS x FROM ss_i) d ON d.id = t.id GROUP BY d.x + 1` now declares the key bigint, where v0.25.4 declared double precision; PostgreSQL declares integer ([numeric-decimal r1](../adr/0012-divergences/numeric-decimal.md)). A grouped product over a derived table that swaps two column names, `SELECT u.b * t.n AS v, count(*) FROM ss_t t JOIN (SELECT id, b AS n, n AS b FROM ss_t) u ON t.id = u.id GROUP BY u.b * t.n`, now answers numeric values where v0.25.4 failed with `cannot store string into FLOAT64 vector`. Through the coordinator these keep their v0.25.4 declarations until ADR-0047 stages 5 and 7. (#1393 and #1649 stay open for the stage-DAG arms)

### Project

[ADR-0047](../adr/0047-a-column-reference-has-one-resolved-identity.md) records the column-identity program: a column reference has one resolved identity, and the stages that carry it from the binder to the stage DAG. [ADR-0024](../adr/0024-decimal-is-finite-fixed-point-with-postgres-result-types.md) gains §10 (the unconstrained NUMERIC column) and §11 (the per-value display scale), and [ADR-0013](../adr/0013-correctness-gates-and-their-boundaries.md) item 11 records the text PostgreSQL may test before or after a set operation chooses its representative. The [ADR-0046](../adr/0046-gate-runners-off-the-host.md) amendment lets the gate-runner dispatcher fall back across equivalent spot pools on a capacity refusal. In CI, the type matrix and the recursive-CTE closure gate skip under `-short` and run in the type-matrix step.
