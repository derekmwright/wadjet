## v0.25.1

A correctness and PostgreSQL compatibility release. `INSERT … VALUES` takes expressions, and every write assigns values by PostgreSQL's assignment rules. Date and time expressions declare PostgreSQL's types. Self-joins and LATERAL joins pair rows by the relation each name refers to. Arrays declare, render and compare as PostgreSQL arrays. **Tables written by `read_json` or `CREATE TABLE AS` over nested values before this release hold Go's text for those values; the first section says how to find and recover them.** Eleven issues close.

### Container values written before v0.25.1

Before this release, `read_json` and `CREATE TABLE AS` over a container expression stored Go's rendering of a nested value. A table created from `read_json` over a record whose `y` is `[1,2,{"z":"w"}]` holds the element `map[z:w]`: on this release it reads `{1,2,map[z:w]}`, and `y[3] ->> 'z'` is NULL. A container cast to text was stored as Go text as well: `CAST(ARRAY[DATE '2024-01-01'] AS TEXT)` stored `[19723]`, the date as its day count, and `CAST(ARRAY[1,2] AS TEXT)` stored `[1 2]`.

The upgrade does not change stored data, and the old text is not converted on read. Rows appended by this release hold JSON and PostgreSQL text, so one column can hold both forms.

**Finding the old rows.** In an array or ROW column, `WHERE CAST(col AS TEXT) LIKE '%map[%'` finds the rows with a Go map in any element, a nested element included. In a text column, use `WHERE col LIKE 'map[%' OR col LIKE '[%'`. A value that really contains such text also matches, JSON array text in a text column included. The [data types page](../data-types.md#nested-types) gives the pattern for an element holding a Go slice.

**The recovery is to read the source again with this release.** Re-running the `CREATE TABLE AS` over the same `read_json` input stores `{1,2,"{\"z\":\"w\"}"}`, and `y[3] ->> 'z'` answers `w`.

### INSERT … VALUES takes expressions

A VALUES cell can be any constant scalar expression: a typed literal, a cast, `CURRENT_DATE`, arithmetic or `CASE`. `INSERT INTO t (d) VALUES (DATE '2026-03-03' + 1), (CAST('2026-01-01' AS DATE))` stores both dates, where v0.25.0 refused every expression with `42601`. (#1252) A column reference is `42703`, a subquery is `0A000`, and `DEFAULT` stores NULL.

VALUES, `INSERT … SELECT`, `UPDATE … SET` and `MERGE` assign through one rule, PostgreSQL's assignment casts. A fractional literal is PostgreSQL's numeric wherever it appears, so `2.5` stores 3 in an integer column. That includes `COALESCE(2.5, 1)`, `ABS(2.5)`, `INSERT … SELECT 2.5` and a CTE that selects it, where v0.25.0's `INSERT … SELECT` stored 2. `2.50` stores `2.50` in a text column, bare or inside `CASE`. An integer expression assigned to a DATE column is `42804`. Division, `SQRT` and `POWER` remain double precision, so `5 / 2.0` and `SQRT(6.25)` store 2 in an integer column (PostgreSQL 3); the [differences page](../postgres-differences.md) lists this.

A DOUBLE PRECISION value assigned or cast to text is PostgreSQL's float8 text, `1234567`. v0.25.0 cast it to `1.234567e+06` and refused the assignment with `42804`. `CAST(2.50 AS TEXT)` is `2.50`, where it was `2.5`.

### Date and time expressions declare PostgreSQL's types

`CURRENT_DATE` and its arithmetic declare DATE: `CURRENT_DATE + 1` is a date, and `CURRENT_DATE + 1 - 1 - CURRENT_DATE` is 0. In v0.25.0 all three were text, and the last answered `18696`. (#1254)

`DATE ± INTERVAL` is a TIMESTAMP: `DATE '1998-12-01' - INTERVAL '90' DAY` is `1998-09-02 00:00:00` (OID 1114), where v0.25.0 answered the text `1998-09-02`. **This changes the value an embedded program receives.** Through `wadjet.DB.Query`, HTTP and gRPC the result is now a TIMESTAMP carried as epoch milliseconds (`904694400000`), like every TIMESTAMP column there already was; v0.25.0 returned the string `"1998-09-02"`.

A quoted operand beside a date or timestamp is read as PostgreSQL reads it: `TIMESTAMP '2026-03-03 10:00:00' + '1 day'` is the next day, and `DATE '2026-03-03' + '1'` is `42725`. `CAST('1 day' AS INTERVAL)` added to a timestamp adds a day, where v0.25.0 added a millisecond. The date/timestamp operators PostgreSQL does not have, such as `DATE - TIMESTAMP`, are `42883`, and `CAST('abc' AS INTERVAL)` is `22007`. v0.25.0 answered `TIMESTAMP + '1 day'`, `DATE + '1'` and `DATE - TIMESTAMP` with numbers, and the invalid interval with the text `abc`.

A DATE or TIMESTAMP past PostgreSQL's range is `22008` in a SELECT or an INSERT (`DATE '2026-01-01' + 2147483647`).

### Unicode escape errors name their location

The Unicode-escape syntax errors carry PostgreSQL's `at or near "…"` suffix: `E'\uDE00'` raises `42601 invalid Unicode surrogate pair at or near "\uDE00"`. Inside an `INSERT … VALUES` row the same message is raised; v0.25.0 reported a generic "unterminated VALUES row". (#1307)

### Self-joins and LATERAL joins pair rows by their own relation

A table joined to itself several times, each copy with its own `ON` condition, pairs each copy's rows through the relation its qualifier names. The three-copy query in #1299 returns PostgreSQL's two rows, where v0.25.0 returned one row that paired the first order's item with the second order's. (#1299)

A LATERAL body's correlated equality can have any expression on its outer side: `WHERE i.k = o.id - 0` returns the matching rows, where v0.25.0 returned none. (#1302) The body's own conditions keep their meaning beside the correlation: `i.v BETWEEN 10 AND 30` no longer loses its upper bound. A select list naming its correlation key under a name another item also uses joins on the key, not the other column. A window in a correlated body is computed per outer row, where v0.25.0 refused it. A `SELECT *` over a LATERAL whose body lists its columns is expanded into the FROM items' own columns, so `ORDER BY 1` over it answers, where v0.25.0 raised `42P10`. A body that is itself `SELECT *` keeps v0.25.0's behaviour: a name it shares with the outer relation is qualified (`s.id`), as the differences page lists. (#1013, #1126)

Four shapes are refused with `0A000` and listed on the [differences page](../postgres-differences.md):

- a window beside a non-equality correlation, or in an ungrouped aggregate body;
- a correlated subquery holding its own LATERAL join inside a LATERAL body;
- a LATERAL nested in another that names the outermost relation;
- a bare `SELECT *` over a LATERAL whose list names one column twice and whose key is an outer expression.

v0.25.0 refused the first shape with a different message. It raised an internal or type error for the second and third, and answered the fourth with no rows.

On the distributed server, a LATERAL runs on the coordinator's single-process pipeline when its arm carries a column name that another relation of the query also has, or when its LEFT join pads a grouped body or a body that publishes a window. Any other LATERAL runs as distributed stages. Running the routed shapes as stages is #1323.

### Arrays declare, render and compare as PostgreSQL's

An array declares PostgreSQL's array type and renders as PostgreSQL's text on pgwire and in the CLI: `SELECT ARRAY[1,2,3]` is `{1,2,3}` (OID 1007), where v0.25.0 sent the text `[1 2 3]`. (#1250, #1017) Through the embedded API it is a Go slice, where it was the string `[1 2 3]`. The element type is declared for a stored or `CREATE TABLE AS` column, a derived table, VALUES and UNION, a zero-row result, and the NULL side of an outer join. (#1133, #1303) A TIMESTAMP or DATE element renders as its text, including in `CAST(… AS TEXT)`: `CAST(ARRAY[DATE '2024-01-01'] AS TEXT)` is `{2024-01-01}`, not `[19723]`. (#1268) `CAST(ARRAY[1,2] AS JSON)` is `[1,2]`. Two output columns of one name keep their own array types. A `UNION ALL` whose first arm is empty returns the other arm's rows, where v0.25.0 returned a NULL.

ORDER BY, MIN and MAX, GROUP BY, join keys and the comparison operators compare arrays element by element under their element type. `ARRAY[50]` sorts before `ARRAY[100]`, and `MAX` of the two is `{100}`; v0.25.0 compared the texts. Arrays whose numeric element types differ meet at their common numeric type, so `ARRAY[1.5] > ARRAY[1]` is true (false in v0.25.0). (#1021) Arrays with no common element type, an integer array beside a text array, are not yet refused as PostgreSQL refuses them; the differences page lists the cases (#1295).

An array of INTERVAL compares by PostgreSQL's interval order, a month counting as 30 days: `ARRAY[INTERVAL '1 month'] = ARRAY[INTERVAL '30 days']` is true. Cast to text it is `0A000`, and projected bare it answers the element's nanosecond count.

A multi-dimensional array renders as `{{1,2},{3,4}}` under OID 25. Its multi-dimensional semantics keep v0.25.0's behaviour: `cardinality(ARRAY[ARRAY[1,2],ARRAY[3,4]])` is 2 (PostgreSQL 4), and `= ANY` over it is `0A000`. The differences page lists these, and #1337 tracks them.

Progress on #679 and #764 is recorded on those issues.
