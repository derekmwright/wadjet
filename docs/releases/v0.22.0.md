## v0.22.0

A join and predicate correctness release. A `SELECT *` over a join publishes
the columns the query wrote, an outer join's `ON` clause is evaluated like any
other predicate, a filter over a cross join keeps only the rows it accepted,
and a predicate that is not a boolean is refused before it removes anything —
where a `DELETE` or an `UPDATE` used to empty a table. Eighteen issues close
across the planner, the executor and the parser; #959 and #655 stay open for
the faces named below.

### What `SELECT *` publishes over a join

The star's output list is the query's own relations, in the order the `FROM`
clause wrote them, under the names PostgreSQL publishes.

- **A `JOIN … USING` star publishes a name the two arms share outside the
  `USING` list**, once per arm — each item bound to its own arm's column — the
  way PostgreSQL publishes it. The statement used to be refused with `0A000`.
  (#1177)
- **A star over a set operation publishes PostgreSQL's names for its unaliased
  items** — `?column?` for an expression, `count` for `COUNT(*)`, the operand's
  name for a cast — on every execution path and in `RowDescription`. It used to
  publish the arm's expression text (`g + 1`, `count(*)`, `cast(g as
  varchar)`), which no client can resolve, and the top-level `UNION ALL`, the
  derived-table spelling and the CTE spelling all did it. (#1079, #1097, #1078)
- **A qualified reference into a derived table or CTE that publishes one column
  name twice raises `42702 column reference "id" is ambiguous`**, as PostgreSQL
  does. It used to answer the first of the two — a value chosen by the block's
  item order, which the client is never told about. A bare star over the same
  block still answers both columns by position, which is also PostgreSQL's
  answer. (#1094)
- **A star over a three-way join declares its columns when the query answers no
  rows** (#1001), a star **beside another select item** over a join answers the
  star's fields plus the item (#1164), and **`ORDER BY <ordinal>` counts
  positions in the star's expanded list** (#1124). All three were refusals.

Four shapes stay refused, each loudly and each on the
[differences page](../postgres-differences.md) with its reason: a chain of
`JOIN … USING`, a positional `ORDER BY` over a `FULL JOIN … USING` merged key,
a qualified star over a block that publishes one name twice, and a
`JOIN … USING` star whose arm is a `LATERAL` body — which publishes the joined
column twice rather than merging it.

One caveat about reading such a result: the PostgreSQL wire carries two output
columns of one name positionally, so `psql` and any pgwire client show both
values, and so does the embedded API's `RowValues`. The `wadjet query`
command's own JSON, CSV and table output is keyed by column NAME, so where two
output columns share one it prints one value under both headings.

### An outer join's `ON` clause is any expression

- **A `LEFT`, `RIGHT` or `FULL` join whose `ON` holds a function call, a
  `CAST`, `LIKE`, `IN`, `CASE`, `BETWEEN` or `IS DISTINCT FROM` is answered**,
  not refused. The condition is evaluated at the join, per probe row against
  each candidate build row, by the same expression compiler an inner join's
  lifted filter runs — so one seam decides what a predicate means, whatever
  join kind it was written on. (#1153)
- **`IS DISTINCT FROM` in an outer join's `ON` rejected every candidate in
  silence**, so a `LEFT JOIN` answered its whole probe side NULL-padded. It
  matches now.
- **A `BETWEEN` inside `ON` is one condition**, not two fragments. The planner
  used to split an `ON` clause into conjuncts on the literal text `" AND "`, so
  `ON a.id = b.id AND a.id BETWEEN 2 AND 3` came apart at the `BETWEEN`'s own
  `AND`. The split reads the parsed condition now. (#1178)
- **An `ON` condition keeps its identity across a stage boundary.** On the
  distributed path a residual over a renamed relation — a derived table, a CTE
  — reached the worker still spelling the subquery's aliases while its sides
  published the base names; nothing resolved, the residual was unknown for
  every candidate pair, and a `LEFT JOIN` answered its whole preserved side
  padded. A reference the rewrite cannot resolve is a refusal now, never a NULL
  at run time.

A subquery in an outer join's `ON` is still refused, and the refusal names the
construct; an inner join lifts the same `ON` above the join and answers it. A
`FULL JOIN` on a non-equi condition answers here, where PostgreSQL has no
executor for it — a superset, listed on the differences page.

### A filter over a cross join

**A cross join no longer publishes the build rows a filter rejected.** A
predicate over one side of a cross join — `FROM a CROSS JOIN b WHERE b.f`, the
comma spelling, or an inner join whose `ON` is an expression — is applied at
that side's scan. When that side is the join's build and arrives in more than
one batch (several files, several row groups, or more than 2048 rows), the
rejected rows came back as live build rows, one copy per probe row:

```sql
SELECT COUNT(*) FROM b2 CROSS JOIN b1 WHERE b1.f
```

answered 52 over a 13-row `b2` and a 5-row `b1` written as three files, where
PostgreSQL answers 39 — and `GROUP BY b1.f` over the same query reported
thirteen surviving rows whose own `f` is `FALSE`. Where every arriving batch
keeps at least one row, which is the ordinary case, what came back was the
whole unfiltered relation per probe row. The build owns its row set now, and
carries it through the merge of its batches, a column prune and a runtime
join-key repair alike. A policed relation's build was never affected: the
policy's projection materializes its rows, so those batches carry no rejected
rows to leak. (#1189)

The same fix closes 65 of the 66 row-count mismatches a 200-database SQLancer
NoREC run reached; the one left is a `FULL` join's `ON` residual, present
before the change as well.

### PostgreSQL's grammar, precedence and pattern language

- **The SQL-standard function spellings parse and answer PostgreSQL 17.11's
  values**: `SUBSTRING(s FROM n FOR m)` and `SUBSTRING(s FROM pattern)` (the
  second operand's type chooses the reading, as it does there),
  `OVERLAY(s PLACING r FROM n [FOR m])`, `NORMALIZE(s [, NFC|NFD|NFKC|NFKD])`,
  `LOCALTIMESTAMP [(p)]`, `LIKE`/`ILIKE`/`SIMILAR TO … ESCAPE`, and
  `LEFT`/`RIGHT` read as function names where a call is legal and as join
  keywords where a join is. `NORMALIZE` performs Unicode normalization; it used
  to strip non-printing characters and call that NFC. A negative `LEFT`/`RIGHT`
  count and both functions over multibyte text answer PostgreSQL's values
  rather than the engine's old byte indexing. (#1169)
- **`#` is the integer XOR operator**, at PostgreSQL's precedence — looser than
  `+` and `-`, tighter than every comparison, left associative. `5 # 3` is 6.
  `^` keeps its own meaning on both engines: `5 ^ 3` is 125. (#1179)
- **`SIMILAR TO` is the SQL standard's pattern language**, not a regular
  expression matched against a substring: `%` and `_` are `LIKE`'s wildcards,
  `|`, `*`, `+`, `?`, `{m,n}`, `()` and `[]` are the regex metacharacters,
  every other character — `.`, `^`, `$` included — is a literal, and the match
  is against the whole string. `'abc' SIMILAR TO 'a%'` is true and
  `'abc' SIMILAR TO 'a.c'` is false; before this release both answers were the
  other way round, and a `WHERE` written this way counted zero rows where
  PostgreSQL counts one. A pattern the translation cannot compile raises
  `2201B` rather than answering NULL. (#1168)
- **A predicate may continue past a `BETWEEN`, an `IN`, a `LIKE` or an `IS`.**
  The predicate band is a precedence loop at PostgreSQL's §4.1.6 table, so
  `5 BETWEEN 10 AND 1 = true` is `(5 BETWEEN 10 AND 1) = true` and answers
  `false`, `1 = 1 IS TRUE` is a statement, and `IS [NOT] UNKNOWN` follows an
  unparenthesized comparison. The forms PostgreSQL refuses stay refused: its
  comparisons are nonassociative, so `1 = 1 = true` is a syntax error here too.
  An unaliased predicate publishes as `?column?`: `SELECT 'abc' SIMILAR TO
  'a%'` used to publish `regexp_like`, the name of the function it was
  rewritten to. (#1180, #1183)
- **A column-alias list on a table function renames its columns**, with or
  without `AS`: `FROM read_json('events.json') f(k, v)` parses, `SELECT k`
  answers the first column's values where it used to answer NULL for every row,
  and a star publishes the list's names. The list is applied where the
  relation's width is known — when the function produces its first batch —
  so a list longer than the relation is `42P10` at execution rather than at
  plan time, and a function that produces no rows is never measured against its
  list. A repeated name in the list is `42701`. (#1184)

Six deliberate differences around these spellings are on the
[differences page](../postgres-differences.md): `LIKE` does not honour the
default backslash escape (write the escape explicitly, which is read exactly as
PostgreSQL reads it), `LOCALTIMESTAMP(p)`'s precision is accepted and ignored,
the clock is read per row, `#` accepts operands PostgreSQL refuses,
`NORMALIZE` also accepts a quoted form, and `SUBSTRING(text SIMILAR pattern
ESCAPE escape)`, `LOCALTIME`, `IS NORMALIZED` and the `U&'…'` literal are not
read at all.

### A predicate that is not a boolean

**Before this release, a `DELETE` or an `UPDATE` whose `WHERE` was a
non-boolean expression removed or changed every row.**

```sql
DELETE FROM t WHERE id > 0 AND CASE WHEN id > 0 THEN 1 ELSE 0 END
```

emptied the table on every door — the embedded API, the PostgreSQL wire and the
HTTP endpoint — where PostgreSQL 17.11 raises `42804 argument of AND must be
type boolean, not type integer` and removes nothing, and where the same
predicate written as a `SELECT` here selected zero rows. One statement, two
answers, and the destructive one was the `DELETE`.

A `WHERE`, a `HAVING`, a `JOIN … ON`, the operands of `NOT`/`AND`/`OR`, a
searched `CASE`'s `WHEN`, a `DELETE`'s and an `UPDATE`'s `WHERE` and a
`MERGE`'s `WHEN … AND` now all require a boolean, with PostgreSQL's own message
and SQLSTATE, and the type is proved from every expression kind the parser
produces: a literal, a column, a call whose declaration is fixed or polymorphic,
a `CASE`, a `CAST`, arithmetic, an `ARRAY` constructor, an `INTERVAL` literal, a
scalar subquery, a `ROW` field path (`(r).a`) and a container subscript
(`arr[1]`, `m['k']` — the element's type, so an `ARRAY<BOOL>`'s element is still
a boolean). A statement refused this way removes and changes nothing.

Where the type cannot be proved — a derived table's or a CTE's column, a
polymorphic call whose mirrored argument this layer cannot type — the clause is
evaluated as before and a non-boolean value reads as false, which selects no
row rather than refusing. A quoted literal is read with the boolean input
function, so `WHERE 'true'` selects every row and `WHERE 'abc'` is `22P02`.

An aggregate in such a clause is `42803` and a window function `42P20`, in the
order PostgreSQL reports them: the window is refused before names resolve, the
aggregate after, so `WHERE SUM(nosuchcolumn) > 0` is `42703`. **A window
function in a subquery's row-filtering clause is refused at plan time** —
`WHERE EXISTS (SELECT 1 FROM z WHERE … AND SUM(o.id) OVER () > 0)` was answered
here on every execution path and is `42P20` now, as it is there. (#1125)
