## v0.21.0

A SQL-surface release: the parser reads four PostgreSQL constructs it did not
read before, a function call is resolved by its arguments rather than by its
name alone, a cast and a literal read the grammar of the type they are for,
and a window key names the relation the query wrote. Nine issues close
across the parser, the expression engine and the planner — #959 and #655 stay
open for the faces named below — and every guide now names the binary that runs
the commands in it.

### Window keys name the relation you wrote

A window's `PARTITION BY` term, its `ORDER BY` term and its function argument
are evaluated over the window's input — the `FROM` clause's relations. A term
written with a table qualifier now names **that** relation's column, and keeps
doing so when another relation of the same join publishes the same bare name:

```sql
SELECT o.id, i.id, COUNT(*) OVER (PARTITION BY o.id)
FROM orders o JOIN line_items i ON i.order_id = o.id
```

partitions on the order's id. Before this release the qualifier was dropped at
planning time and the key bound whichever side the planner chose to build, so
this query put every row in its own partition and answered 1 where PostgreSQL
answers 2 — silently, and differently if you wrote the `FROM` clause the other
way round or added a predicate that changed the plan's cost estimate. The same
binding covers the window's function argument, the `ORDER BY` inside an `OVER`
clause, a sort key, and a window under `QUALIFY`.

A term that is an expression (`PARTITION BY o.id + 0`) is computed into a
column of its own before the window runs, and a key naming no column of the
window's input is a refusal rather than a silent single partition.

**One exception, on `wadjetd`.** A qualified term naming a correlated `LATERAL`
arm binds the outer relation's column of that bare name when the query runs
through the stage DAG; the embedded binary and PostgreSQL bind the lateral
body's own. It is listed with its mechanism in
[PostgreSQL differences](../postgres-differences.md).

(#1028)

### PostgreSQL grammar the parser now reads

- **`BETWEEN SYMMETRIC` and `BETWEEN ASYMMETRIC`**, with or without `NOT`, in
  every position a `BETWEEN` may be written. `SYMMETRIC` does not require the
  lower bound first: `5 BETWEEN SYMMETRIC 10 AND 1` is true. It is
  `(a BETWEEN b AND c) OR (a BETWEEN c AND b)`, PostgreSQL's own expansion —
  not `BETWEEN least(b,c) AND greatest(b,c)`, which answers true for
  `1 BETWEEN SYMMETRIC NULL AND 1` where PostgreSQL answers NULL. A NULL
  operand anywhere makes the answer NULL. (#1154)
- **The `^` exponentiation operator**, at PostgreSQL's documented precedence:
  tighter than `*` `/` `%`, looser than unary minus (`-2 ^ 2` is 4), and LEFT
  associative, so `2 ^ 3 ^ 2` is 64 and not 512. It is `POWER(a, b)` under
  another spelling and shares that function's values and error classes —
  `POWER(0, -1)` and a negative base with a fractional exponent are `2201F`, an
  overflow is `22003`
  — and it publishes as `?column?`, which is what PostgreSQL publishes for an
  operator. PostgreSQL's integer XOR is `#`, which this engine does not
  implement; `^` is not it. (#1155)
- **A column-alias list on any `FROM` item** — a base table, a derived table, a
  `VALUES` block and a `WITH` query — with or without `AS`:
  `FROM flow_logs f(k, v)`, `FROM (VALUES (1), (2)) v(n)`. The list opens a new
  relation namespace, so a name it renamed away is `42703` and the table's own
  name is `42P01`, as PostgreSQL has them, and a list longer than the relation
  is `42P10`. A star above such a relation applies the rename, which also
  repairs `SELECT b.* FROM (SELECT …) b(k, v)` — that answered NULL for every
  renamed column. Two narrowings are recorded in
  [PostgreSQL differences](../postgres-differences.md): a REPEATED name in the
  list is `42701` here, and a list on a `WITH`-query **reference** is `0A000` —
  put it on the definition, `WITH c(x, y) AS (…)`, which answers. A table
  function is not in the list above: it takes a column-alias list only after
  `AS` and does not apply it, so the renamed name answers NULL. (#1158; #959 in
  part)
- **`SELECT *` over `JOIN … USING` merges the joined column**, publishing it
  once and first, then each arm's remaining columns — three output columns for
  two two-column tables where the same join written with `ON` publishes four.
  The merged value is the left arm's column for an `INNER` or `LEFT` join, the
  right arm's for a `RIGHT` join, and `COALESCE(left.c, right.c)` for a `FULL`
  join. A qualified star names one side and merges nothing, and a bare
  `ORDER BY` over the merged column, or a window key over a `RIGHT` join's,
  binds the merge rather than the left arm — which matters because the left
  arm's column is NULL on exactly the rows the merge took from the other side.
  A `USING` clause may follow another join on the same `FROM` item when that
  earlier join is itself an inner `JOIN … USING` naming the same columns, which
  is PostgreSQL's own bound, and `CROSS JOIN … USING` is `42601`.
  `NATURAL JOIN` is still refused; so is a bare reference to the merged column
  outside a sort or window key (qualify it, which resolves), a window key naming
  a `FULL` join's merged column (write the expression, or use `ON`), a bare
  `SELECT *` over a `FULL` join ordered by the merged column (name the other
  columns and qualify the merged one, which answers), a star over a chain of
  `USING` joins, and a star over a `USING` join whose arms share a column name
  outside the `USING` list. Each is on the differences page with its reason.
  (#655, in part)

### Functions, casts and literals read the right grammar

- **A call is resolved by its name AND its arguments.** Every function takes
  the number of arguments its documented signature shows, and a call with any
  other count is **`42883`** at plan time, with PostgreSQL's message:
  `function upper(unknown, unknown) does not exist`. Before this release a
  wrong count reached the function body, which answered NULL or dropped the
  extra argument — and a filter over such a call then evaluated NULL for every
  row and silently dropped the whole relation. A numeric literal in a text
  position is the same refusal (`UPPER(1)`, `LPAD(1, 3, '0')`), where it used to
  answer the number's text or, at a vectorized kernel, fail the query with an
  internal error; `CONCAT`, `CONCAT_WS` and `||` render any argument, exactly
  as PostgreSQL does. A **column** of another type is still rendered as
  its text (`UPPER(mac_col)`), which is a deliberate superset. (#1053, #1056)
- **Text-only functions over `BYTES` refuse**, which is what PostgreSQL answers
  for `upper(bytea)`: reading those bytes as whatever text they spell is a
  wrong value, not a convenience. `ENCODE`, `DECODE`, `GET_BYTE` and `SET_BYTE`
  are new and are the bridge between the two families; the functions
  PostgreSQL does have over `bytea` keep working — `LENGTH`, `OCTET_LENGTH`,
  `BIT_LENGTH`, `SUBSTRING`, `MD5`, `POSITION` and `||`. `GET_BYTE` declares
  `integer` on the wire. (#583)
- **`TRIM` takes a character set.** `TRIM([BOTH|LEADING|TRAILING] chars FROM s)`
  and the two-argument `TRIM(s, chars)` / `LTRIM` / `RTRIM` remove every
  leading or trailing character that is IN the set: `TRIM(BOTH 'ab' FROM
  'baXab')` is `X`. The cutset used to be parsed and dropped.
- **A cast to an integer type reads its operand's own grammar.** PostgreSQL has
  two casts here and they are not the same cast: `'2.5'::integer` is `22P02`
  because the text form has no fractional part, while `numeric_col::integer`
  rounds half away from zero. `CAST('2.5' AS INTEGER)` answered 3 here and
  reached storage that way through `INSERT … SELECT` and `CREATE TABLE … AS`;
  it is now `22P02` for a quoted literal, a `STRING` column, a container
  element, a MAP value, a scalar subquery and any string-typed expression,
  while a DECIMAL or float operand still rounds. The rule covers `INTEGER`,
  `BIGINT`, `SMALLINT`, `INT32`, `INT64`, `PORT` and `PROTOCOL`. (#1141)
- **A literal beside a `PORT` or `PROTOCOL` column reads that type.**
  `WHERE proto = 'udp'` answers the UDP rows where it used to be `22P02`, and
  `WHERE port = '0x1bb'` is `22P02` where it used to match port 443 through
  int4's radix grammar — the same two answers the writer and `CAST` give. It
  holds in `=`, `<>`, `IN`, `BETWEEN`, `CASE`, `COALESCE`, a join `ON` and a
  `HAVING`, and the row-group prune reads the literal the way the filter does,
  so a pruned file cannot disagree with a scanned one. (#1137)
- **A refusal never names an internal type identifier.** Writing bad text into
  a `BIGINT` column through `INSERT … SELECT`, a `CAST` or a predicate reports
  `bigint`, the name a client can resolve in `pg_type`, rather than the engine's
  own `INT64`.

### Documentation

- **[How wadjet differs from PostgreSQL](../postgres-differences.md)** is one
  page listing every deliberate difference — values, declared types, errors and
  refusals, ordering, extensions, and what is not supported — with the shape
  that shows each one. Anything not on that page is a bug worth reporting.
- **Every command in the guides names the binary that runs it** — `wadjet` for
  the CLI and the embedded server, `wadjetd` for a cluster — across the README,
  getting-started, runbook, distributed and API guides, down to the build
  target the container examples use.
- **The SQLancer fuzzer runs against the MIT embedded server.**
  `task sqlancer:run-mit` starts `dist/wadjet serve` on a scratch store, runs
  the chosen oracle against it and stops the server when the run ends;
  `task sqlancer:triage` sorts the findings, reading the differences page so a
  documented difference is classified as one rather than counted as a defect.
  See `tools/sqlancer/README.md`.
