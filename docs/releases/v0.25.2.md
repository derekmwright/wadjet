## v0.25.2

A correctness and PostgreSQL compatibility release. A float parameter bound over pgwire is a value of its own type. A membership test against a subquery types both of its sides by one rule. Set operations follow PostgreSQL's precedence. An integer column rounds a value by the type PostgreSQL gives it. **The first section lists what a client or a stored query sees differently after the upgrade.** Nine issues close: #1308, #1349, #1368, #1369, #1370, #1372, #1373, #1374 and #1353.

### Behaviour changes

**Float parameters bind as floats.** A float8 or float4 parameter bound over pgwire is a value of its own type, as in PostgreSQL. `SELECT $1` over a float8 parameter declares double precision (OID 701), and over a float4 one real (OID 700); v0.25.1 declared both numeric (OID 1700), the float8 one in the text and the binary format. A `CREATE TABLE … AS SELECT $1` column is double precision, where it was numeric. Arithmetic over the parameter is float arithmetic: `ROUND($1)` over 2.5 answers 2 (v0.25.1: 3), and `$1 / 2` over 5 answers 2.5 (v0.25.1: 2). `NaN` and `Infinity` bind, where v0.25.1 raised 42703 for them in the text format. A float8 2.5 assigned to an integer column by `MERGE … UPDATE SET n = $1` stores 2, where v0.25.1 stored 3. A parameter declared numeric (OID 1700) is unchanged. (#1353)

**A membership's numeric literal past 38 digits is refused.** A numeric literal compared with a NUMERIC subquery, as in `'…' IN (SELECT numeric_col …)`, that this engine's 38-digit DECIMAL cannot hold exactly raises 22003 `numeric field overflow`. That covers more than 38 significant digits (`'14.0000000000000000000000000000000000000001'`), a digit past scale 38 (`'1e-40'`), an integer past 38 digits (`'1e40'`), NaN and ±Infinity, whether the literal is quoted, under `CAST(… AS NUMERIC)` or unquoted, and for `NOT IN` as well. PostgreSQL answers these: `IN` finds no row and `NOT IN` keeps every row. v0.25.1 answered the quoted spelling the same way, and its CAST and unquoted spellings of a literal with more than 38 significant digits found every row for `IN`; for the other literals it answered as PostgreSQL does. Zeros that carry no value do not count, so `'12.5'` followed by forty zeros is 12.5 and matches it (v0.25.1: no row). The [differences page](../postgres-differences.md) lists the refusal. (#1372)

**Statements v0.25.1 answered that are now refused.** The following now raise PostgreSQL's error:

- A typed value compared with a subquery that selects TEXT, such as `bigint_col IN (SELECT text_col …)`, is `42883`. v0.25.1 answered no rows, or every row for `NOT IN`.
- A recursive CTE whose term reaches itself inside a parenthesised or derived-table `INTERSECT ALL` or `EXCEPT ALL` is `42P19`. v0.25.1 answered it.
- An aggregate in an `UPDATE` or `MERGE` `SET` list (`SET n = MAX(n)`), in an `INSERT … VALUES` cell or in a MERGE `WHEN` condition is `42803`; v0.25.1 stored NULL (or skipped the clause).

A window function in a `SET` list is `42P20`, where v0.25.1 refused it with `0A000`. `sqrt`, `exp`, `ln` or `power` applied to a numeric constant and compared with a subquery (`sqrt(12.5 * 12.5) IN (SELECT numeric_col …)`) is refused with `0A000`, where PostgreSQL answers and v0.25.1 answered in double precision; a float-only function combined with a numeric constant there (`sin(0.0) + 12.5 IN (…)`) is refused the same way, where PostgreSQL and v0.25.1 answered (#1420). The differences page lists this refusal. The sections below give the details.

### Typed values against a TEXT subquery

A typed value compared with a subquery that selects TEXT raises `42883 operator does not exist: bigint = text`, as PostgreSQL does and as an explicit JOIN on the same pair already did. The rule covers `IN`, `NOT IN`, `= ANY` and `<> ALL` over a stored text column, a derived table, a CTE, a text literal selected `FROM` a table and a `UNION ALL` of such literals. It also covers `EXISTS` and `NOT EXISTS` bodies that equate a typed column with a text column. v0.25.1 answered all of these. Over a stored column it found no row for `IN`, `= ANY` and `EXISTS` and every row for `NOT IN`, `<> ALL` and `NOT EXISTS`. (#1308)

A body that selects `CAST(x AS TEXT)` still compares through the text when that text renders every value as the compared type does: the same type, two integer kinds, or PORT and PROTOCOL against a double. `bigint_col IN (SELECT CAST(bigint_col AS TEXT) …)` matches, as in v0.25.1. A cast whose text renders differently is `42883`, in `IN` and as an `EXISTS` key alike. `numeric_col IN (SELECT CAST(bigint_col AS TEXT) …)` found one row in v0.25.1 and its `EXISTS` spelling none (#1374). `bigint_col IN (SELECT CAST(numeric_col AS TEXT) …)` found none. A literal body with no `FROM`, `IN (SELECT '12')`, is read as an `IN` list and matches. PostgreSQL refuses the kept cast bodies and the `FROM`-less literal body, and the differences page lists both.

### Set operations follow PostgreSQL's precedence

`INTERSECT` binds tighter than `UNION` and `EXCEPT`, as in PostgreSQL. `SELECT 1 UNION SELECT 2 INTERSECT SELECT 2` is `1 UNION (2 INTERSECT 2)` and answers 1 and 2. v0.25.1 read every chain left to right and answered 2. `UNION` and `EXCEPT` still associate left to right, and parentheses override: `(SELECT 1 UNION SELECT 2) INTERSECT SELECT 2` answers 2. (#1349)

A recursive term can be an `INTERSECT` chain, as in `WITH RECURSIVE r(n) AS (SELECT 1 UNION ALL SELECT n + 1 FROM r WHERE n < 5 INTERSECT SELECT 2) …`, which answers 1 and 2. v0.25.1 refused it with `42P19`. A recursive term that reaches its own CTE under `INTERSECT ALL`, on the right of `EXCEPT` or on the left of `EXCEPT ALL` raises PostgreSQL's `42P19` (`recursive reference to query "r" must not appear within INTERSECT`). v0.25.1 answered the parenthesised and derived-table spellings of the `INTERSECT ALL` and `EXCEPT ALL` cases.

### A membership types both sides by one rule

A membership against a subquery types its two sides by one rule, whatever their shape.

- A quoted literal takes the subquery's type, as in PostgreSQL. `'12' IN (SELECT bigint_col …)` matches 12, and `'2024-1-2' IN (SELECT date_col …)` matches `2024-01-02`; v0.25.1 found no row (every row for `NOT IN`). A literal that is no value of the type is `22P02` (`'zz'`), where v0.25.1 found no row. (#1372)
- A numeric literal compared with a NUMERIC subquery is the exact number its text spells: `12500000000000.0001 IN (SELECT numeric_col …)` finds no row when the member is 12500000000000.0000. v0.25.1 found every row for the unquoted and `CAST(… AS NUMERIC)` spellings. (#1372)
- An outer value computed from numeric constants is compared as the exact number it computes. `COALESCE(14.0000000000000000001, 0)`, `CASE … THEN 14.0000000000000000001 END` and `-(-14.0000000000000000001)` do not match 14, where v0.25.1 found every row. `CAST(16777216 AS NUMERIC) IN (SELECT integer_col …)` matches, where v0.25.1 found no row and answered false in the select list. (#1372)
- A DATE compared with a `UNION`, `UNION ALL` or expression subquery (`SELECT date_col + 0 …`) matches by value; v0.25.1 found no row (every row for `NOT IN`). (#1373)
- A typed expression outside (`bigint_col + 0 IN (SELECT text_col …)`) and a TEXT expression inside (`IN (SELECT upper(text_col) …)`) are `42883`, where v0.25.1 answered (#1369, #1370). So is a LATERAL body's correlated key that equates a text column with a typed one, where v0.25.1 answered no rows (#1368).
- An `IN (SELECT max(x) … GROUP BY …)` whose aggregate has no alias answers, where v0.25.1 raised an internal plan error (`42000`).

`CAST(text AS NUMERIC(p,s))` of text written with more than 38 digits rounds into the declared scale, as PostgreSQL does. `CAST('1.00000000000000000000000000000000000000001' AS NUMERIC(10,2))` is 1.00, where v0.25.1 raised `22003`.

### Integer columns round by PostgreSQL's type

An integer column assigned a value that PostgreSQL types numeric rounds it half away from zero on every write. That includes division, `SQRT`, `POWER`, `EXP` and `LN`, which this engine computes in double precision. `INSERT INTO t VALUES (5 / 2.0), (SQRT(6.25)), (POWER(2.5, 1))` stores 3, 3, 3, where v0.25.1 stored 2, 2, 2. The same holds through a derived table or a CTE in `INSERT … SELECT`, and in `UPDATE … SET n = 5 / 2.0` (3; v0.25.1 2). (#1353)

A double-precision source rounds half to even, as in PostgreSQL, so `POWER(2, -1)` stores 0. `NULLIF(2.5, f)` over a double column `f` is a double in PostgreSQL and stores 2 (v0.25.1: 3). A double column read through `MERGE … USING (SELECT …)` stores 2 for 2.5 and 0 for 0.5 (v0.25.1: 3 and 1). A MERGE action's `SET n = (SELECT MAX(f) …)` over the same 2.5 also stores 2 (v0.25.1: 3).

A write that PostgreSQL refuses now writes nothing:

- An aggregate in an `UPDATE` or `MERGE` `SET` list is `42803`, and a window function is `42P20`.
- A name that a MERGE subquery source publishes twice is `42702`, where v0.25.1 ran the MERGE.
- A JSON field read assigned to an integer in a MERGE action (`SET n = s.j ->> 'k'`) is `42804`, where v0.25.1 stored 3 for `2.5`.
- Arithmetic between a text column and a number (`x * 1`) is `42883`, where v0.25.1 answered NULL.

A double on the left of `+` that no date can be shifted by answers its sum. `CAST('Infinity' AS DOUBLE PRECISION) + 1` is `Infinity`, and `CAST('1e300' AS DOUBLE PRECISION) + 1` is `1e+300`, where v0.25.1 raised `22008 date out of range`.

A `LIMIT` count written as a float cast counts: `LIMIT CAST('1' AS DOUBLE PRECISION)` returns one row, where v0.25.1 raised `42601`. A float8 parameter whose text is `+1` counts too, where v0.25.1 raised `42601`.

An explicit `CAST(5 / 2.0 AS INTEGER)` still answers 2 (PostgreSQL 3); the differences page lists it (#1392).

### Development

The issue-worker workflow's failure-comment step declared two `env:` blocks, which GitHub rejects, so every push to `main` recorded a failed run with no jobs. The step now has one `env:` block.
