## v0.25.3

A correctness and PostgreSQL compatibility release. A subquery predicate whose probe is a constant answers over a query that reads the subquery's table more than once. A DATE compared with a TIMESTAMP compares at the DATE's midnight in memberships, correlations, join keys and scalar subqueries. A window function reads a literal argument and its integer argument as PostgreSQL does. ADR-0012's divergences from PostgreSQL are now a catalog with one row per SQL cell. **The first section lists what a client or a stored query sees differently after the upgrade.** Five issues close: #1382, #1418, #1378, #1394 and #1399.

### Behaviour changes

**Statements v0.25.2 answered that are now refused.**

- A `CASE`, `COALESCE`, `GREATEST` or `LEAST` that mixes a DATE and a TIMESTAMP is `0A000`; `CAST` the DATE arm to TIMESTAMP, which answers as PostgreSQL does. The refusal holds whether an arm is a column of a table, a derived table or a CTE, a scalar subquery or a window call. v0.25.2 answered a DATE arm in a TIMESTAMP result as its day count read as milliseconds (`COALESCE(ts, d)` over the DATE 2024-05-06 answered `1970-01-01 00:00:19.849`), or raised `22003`. (#1378)
- `COALESCE(ts, (SELECT max(d) …))`, a TIMESTAMP with a DATE scalar subquery, is refused too, although v0.25.2 printed it as PostgreSQL does in a bare projection. Its value was wrong once read: `CAST(… AS VARCHAR)` answered epoch milliseconds (`1704153600000`) for the TIMESTAMP rows, and `+ INTERVAL '1 hour'` left those rows unchanged. (#1378)
- Arithmetic, `sum`, `avg` and an integer comparison over a DATE or TIMESTAMP column that a derived table computes with a scalar subquery or a window call raise `42883`, as `ts + 1` and `sum(d)` do over a stored column. v0.25.2 answered a number: `ts + 1` answered `1.709510400001e+12`, the `sum` of a DATE its day count, `19849`, and `d IN (SELECT bigint_col …)` no rows. (#1378)
- A window function's per-row integer argument is `0A000`: a column (`LAG(x, o)`, `NTILE(o)`), an expression over one (`LAG(x, o + 1)`) or a subquery (`LAG(x, (SELECT 2))`). Write a constant. v0.25.2 read a column argument as 1, and answered the subquery offset as PostgreSQL does. (#1399)
- A window function's integer argument that PostgreSQL refuses raises its error. A numeric or bigint argument (`LAG(x, 1.5)`, `LAG(x, CAST(0 AS BIGINT))`) is `42883`. A quoted one that is not an integer (`'1.5'`) is `22P02`, and an integer expression past int4 (`2147483647 + 1`) is `22003`. `LAG(x, 1 / 0)` is `22012`, `NTILE(0)` is `22014` and `NTH_VALUE(x, 0)` is `22016`. v0.25.2 read each of these as 1. The error is raised even for a column an enclosing query does not read: `SELECT count(*) FROM (SELECT NTILE(0) OVER (…) AS a FROM t) s` is `22014`, where v0.25.2 and PostgreSQL answer the count (#1437). (#1399)
- A `LAG` / `LEAD` whose value argument is a literal and whose default is not a numeric literal or NULL (`LAG(FALSE, 1, TRUE)`) fails the query with `42000` (#1436); v0.25.2 answered NULL on every row.

**Answers that change.** Over a self-join, `99 NOT IN (SELECT v FROM t)` and `99 <> ALL (SELECT v FROM t)`, whose probe is absent, answer every row, where v0.25.2 answered none. `ts NOT IN (SELECT d …)` removes the TIMESTAMPs at a DATE's midnight, which v0.25.2 kept. `LAG(x, 0)` answers the current row, where v0.25.2 answered the previous one. A literal window argument (`SUM(2.5) OVER ()`) answers its value, where v0.25.2 answered NULL. The sections below give the details.

### A constant subquery probe over a join

An uncorrelated subquery predicate whose probe is a constant or a bound parameter answers when the query reads the subquery's table more than once: a self-join, a comma join, or an `IN` subquery over the same table beside it. That covers `12 IN (SELECT q.v FROM t q)`, `'12' IN`, `CAST('12' AS BIGINT) IN`, `= ANY`, `NOT IN` and `<> ALL`. It also covers `EXISTS (SELECT 1 FROM t q WHERE q.v = 12)`, `NOT EXISTS` and a scalar comparison, `(SELECT q.v FROM t q WHERE q.id = 1) = 12`. v0.25.2 answered no rows, `NOT IN` and `<> ALL` included, where PostgreSQL answers every row. It failed `EXISTS`, and `NOT EXISTS` over a plain constant, with `filter column "q.v" does not exist in the input schema`. A `NOT EXISTS` whose probe is a `CAST` or an arithmetic expression (`q.v = 6 + 6`) answered every row, where PostgreSQL answers none. (#1382, #1418)

The same subquery in the select list answers true. v0.25.2 answered NULL for `IN` and `NOT IN`, took a `CASE`'s `ELSE` arm, and failed for `EXISTS`. A `UNION ALL` of such a query with another scan of the table answers, where v0.25.2 gave no answer within 30 seconds. A scalar subquery over the table that an enclosing `IN` subquery reads, as in `a.k IN (SELECT b.k FROM d b WHERE b.k > (SELECT AVG(c.k) FROM d c))`, answers too. v0.25.2 gave no answer to it within 30 seconds.

### A DATE against a TIMESTAMP

A DATE compared with a TIMESTAMP compares the DATE's midnight, as PostgreSQL does, in these places:

- an `IN`, `= ANY`, `NOT IN` or `<> ALL` subquery;
- an `EXISTS` or `LATERAL` correlation;
- a join key, a `WHERE` equality between two tables' columns included;
- a comparison with a scalar subquery.

v0.25.2 compared the TIMESTAMP's milliseconds since 1970 with the DATE's day number there. `ts IN (SELECT d …)` found no row for 2024 values but matched `1970-01-01 00:00:00.001` to the DATE 1970-01-02, and `NOT IN` kept the rows at a DATE's midnight and removed that one. Against a scalar subquery, `ts = (SELECT d …)` for the DATE 1970-01-02 matched `1970-01-01 00:00:00.001` as well as the midnight, and `ts < (SELECT d …)` dropped that row. (#1378)

The first section lists the `CASE`, `COALESCE`, `GREATEST` and `LEAST` refusal and the `42883` refusals. A set operation that mixes a DATE and a TIMESTAMP stays refused with `0A000`, as in v0.25.2. A bind parameter typed TIMESTAMP against a DATE column is still read at DATE (#1426): `d = $1` with `2024-01-02 12:00:00` matches the DATE 2024-01-02, where PostgreSQL finds no row. `d = CAST($1 AS TIMESTAMP)` compares as PostgreSQL does.

### A window function's arguments

A literal VALUE argument answers its value. Over three rows, `SUM(2.5) OVER ()` is 7.5, `FIRST_VALUE(2.5) OVER (ORDER BY id)` and `MAX(2.5) OVER ()` are 2.5, and `SUM(2) OVER ()` is 6. `LAG(5) OVER (ORDER BY id)` is NULL on the first row and 5 after it. v0.25.2 answered NULL for each. `SUM(2.5) OVER ()` declares numeric, where v0.25.2 declared double precision. `INSERT … SELECT SUM(2.5) OVER ()` over one row stores 3 in an integer column, 2.50 in a `NUMERIC(10,2)` one and 2.5 in a double. v0.25.2 stored NULL. A text literal given to `FIRST_VALUE` answers the text, where v0.25.2 answered NULL and PostgreSQL raises `42804`; the differences page lists it. (#1394)

The integer argument (`LAG` and `LEAD`'s offset, `NTILE`'s bucket count, `NTH_VALUE`'s n) is an `integer`, as in PostgreSQL. The operator honors it as written:

- `LAG(x, 0)` and `LEAD(x, 0)` answer the current row. v0.25.2 answered the previous and the next row, and `LAG(x, 0)` answered NULL under `PARTITION BY id`.
- A negative offset reads the other way: `LAG(x, -1)` is the next row, where v0.25.2 answered the previous one.
- `LAG(x, NULL)` is NULL on every row, where v0.25.2 answered the previous row.
- A quoted integer (`'2'`), `CAST(2 AS INTEGER)` and a constant expression are read by value. `LAG(x, 1 + 1)` reads two rows back and `NTILE(abs(-2))` makes two buckets; v0.25.2 read one row back and made one bucket.
- An offset past the partition's edge answers the default: `LAG(x, -2147483648, 7)` is 7 on every row, where v0.25.2 answered 7, 10, 20.
- A bound integer parameter is read the same way: `LAG(x, $1)` with 0 answers the current row, where v0.25.2 answered the previous one.

`LAG(x, '1' + 1)` is `42883`, where PostgreSQL reads 2 and v0.25.2 read 1. The first section lists the other refusals. (#1399)

### Documentation

ADR-0012's deliberate divergences from PostgreSQL are now a catalog in `docs/adr/0012-divergences/`: 295 rows in 16 families. Each row is one SQL cell, with PostgreSQL's answer, this engine's, the SQLSTATE, the disposition and the gate that pins it. ADR-0012 §5 states the rule, and `docs/adr/0012-amendments.md` is the dated log. Every entry of the [differences page](../postgres-differences.md) names the catalog row behind it.

Sixteen entries where the differences page and the ADR disagreed now carry the answer this engine gives. The engine did not change for any of them, but the page now says:

- An arm that publishes one name twice under `SELECT *` over `JOIN … USING` is `0A000`; the page said `42702`.
- `SUM` and `AVG` over DURATION declare double precision.
- `SUM(b * 1)` and `SUM(ABS(b))` over a bigint column declare numeric and answer past bigint.
- Grouped `MIN` over REAL declares real, as PostgreSQL does, so the entry is gone.
- The operator spellings `<<`, `>>` and `&` are `42601`; `BITWISE_LEFT_SHIFT(2147483647, 2)` is `8589934588`.
- `TIME_BUCKET` accepts a `CAST(… AS INTERVAL)` stride. A text stride is `42804`, and `INTERVAL '1 day 6 hours'` is `22007`.
- `CAST('abc' AS VECTOR(3))`, `AS INTEGER[]` and `AS IPV4` raise `22P02`, and `CAST(ARRAY[1,2] AS VECTOR(2))` is `[1,2]`. Only DURATION and BYTES pass text through.
- `CAST(ARRAY[1] AS DATE)` is `42846`, as in PostgreSQL. `CAST(true AS DATE)` is still NULL.
